# Decision Log

Append-only. Every entry: what was decided, what the alternative was, and why. This file is where the "why did you build it that way?" questions get answered.

Format: `## NNN — Title` / **Decision** / **Alternative** / **Reasoning** / **Trade-off accepted**

---

## 001 — PostgreSQL, not MongoDB

**Decision:** PostgreSQL 16 with a `JSONB` column for flexible attributes.
**Alternative:** MongoDB Atlas, on the grounds that garments are polymorphic.
**Reasoning:** The garment schema is regular, not polymorphic — 13 attributes that apply to nearly everything. What is genuinely complex is the *relationships*: users to items, looks to items many-to-many, wear history. That is precisely where a relational database is strong. `JSONB` covers the flexible tail, and `pgvector` remains available for free if semantic search is ever wanted.
**Trade-off accepted:** Schema changes require migrations. This is a feature at this scale, not a cost.

## 002 — No retrieval layer, no vector database

**Decision:** The entire wardrobe is serialised into every stylist prompt.
**Alternative:** Embeddings plus a vector store, retrieving the top-k relevant items.
**Reasoning:** A realistic wardrobe is 80–150 items, roughly 4,000 tokens in compact form. It fits in one request and costs a fraction of a cent. Retrieval would add infrastructure and a failure mode to solve a problem that does not exist below ~400 items. Aggressive filtering also actively *hurts* quality — excluding "summer" items in winter blocks the summer-dress-with-boots-and-jacket combinations that make the product feel intelligent.
**Trade-off accepted:** Does not scale past ~400 items. The two-pass fallback is documented in `03-AI-CONTRACTS.md` and intentionally not built.

## 003 — `warmth` 1–5, not `season`

**Decision:** Insulation as an ordinal 1–5 property of the garment.
**Alternative:** A `season` enum.
**Reasoning:** Season is location-dependent. A Tel Aviv winter is 14°C; a Tel Aviv October is 30°C. "Winter garment" is not a stable property of a garment, but insulation is. It also maps directly onto a real temperature, which is what the weather rules compare against.
**Trade-off accepted:** Slightly less intuitive as a label. Mitigated with concrete anchors in the prompt and the UI.

## 004 — Weather rules computed in Python, not inferred by the model

**Decision:** Temperature is converted to an explicit instruction string by a pure function before the prompt is assembled.
**Alternative:** Send the raw temperature and let the model reason.
**Reasoning:** Model reasoning over raw numbers is inconsistent between calls, which is unacceptable for the feature users will judge the app on. A lookup table is deterministic, and it is unit-testable with zero AI calls — 12 assertions covering every boundary.
**Trade-off accepted:** Less nuance than a model might apply. Reliability is worth more here.

## 005 — Closed vocabulary for every attribute

**Decision:** Every descriptive field is an enum. Anything outside it fails validation.
**Alternative:** Free-text tags from the vision model.
**Reasoning:** Free text produces `light blue`, `baby blue`, `sky blue` and `pale blue` for one garment. Filtering, grouping, and stylist reasoning all degrade. A closed vocabulary makes exact matching reliable and makes invalid output detectable.
**Trade-off accepted:** Some expressiveness lost. `attributes JSONB` and `display_name` absorb the nuance that matters.

## 006 — `BackgroundTasks`, not Celery

**Decision:** FastAPI `BackgroundTasks` for asynchronous tagging.
**Alternative:** Celery with Redis.
**Reasoning:** Celery adds a broker, a worker process, more configuration, and more failure modes to handle at most 20 jobs per session. `BackgroundTasks` runs the coroutine after the response is sent, which is the entire requirement.
**Trade-off accepted:** Jobs are lost on process restart. Mitigated with a startup sweep and a manual retag endpoint.

## 007 — Polling, not WebSockets

**Decision:** The frontend polls every 2 seconds while items are processing.
**Alternative:** WebSocket push.
**Reasoning:** Polling is ~15 lines, works through every proxy, and survives Render free-tier idling. WebSockets would be correct at scale; at 20 items per session they are unjustified complexity.
**Trade-off accepted:** Up to 2 seconds of latency and some wasted requests. Both are invisible to the user.

## 008 — Uploads route through the backend

**Decision:** Browser → FastAPI → Cloudinary.
**Alternative:** Signed direct browser-to-Cloudinary upload.
**Reasoning:** Routing through the backend guarantees that every stored asset has a matching database row. Direct upload produces orphaned media whenever a client drops mid-flow.
**Trade-off accepted:** One extra network hop and backend memory during upload. Bounded by a 10 MiB per-file limit.

**Amended at task 0.7 — "bounded by a limit" was measured and is only half true.** The unit is mebibytes, as `CONVENTIONS.md` requires; the original wording said MB, which differs by 5%. More importantly, the bound applies to *process memory*, not to what the request costs the machine. Starlette parses and spools the entire multipart body before the handler is entered, and `MultiPartParser.spool_max_size` is 1 MiB, so every part above that rolls to a temporary file on disk. Twenty 10 MiB files therefore cost ~200 MB of ephemeral disk regardless of any check our code performs. What task 0.7's size pass buys is that only one file's bytes are ever resident in RAM — peak RSS of roughly 10 MiB instead of 200 MB. See 048 for how, and `07-DEPLOYMENT.md` for the residual disk risk and its owner.

## 009 — Curated styling knowledge, not a web-search agent

**Decision:** Styling principles are written into the system prompt.
**Alternative:** An agent with a web-search tool fetching current trends.
**Reasoning:** Fashion queries return SEO spam and commerce pages. The agent would add seconds of latency and non-determinism in exchange for generic advice. A curated prompt is free, fast, deterministic, testable, and under our control.
**Trade-off accepted:** Not aware of this week's trends. For a wardrobe-combination tool this is close to irrelevant.

## 010 — One stylist call per trip, not one per day

**Decision:** The whole trip is a single call.
**Alternative:** One call per day.
**Reasoning:** Per-day calls are blind to each other's choices and therefore cannot reuse items. Reuse is the entire point of a packing list.
**Trade-off accepted:** A larger prompt and a longer single response. Chunk at 7-day blocks if quality degrades, carrying already-packed items forward.

## 011 — No refresh token

**Decision:** A single 7-day JWT.
**Alternative:** Short access token plus refresh token rotation.
**Reasoning:** Refresh rotation is meaningful for a production application with real session-security requirements. Here it is a day of work and a class of bugs, for a capstone with a demo account.
**Trade-off accepted:** A leaked token is valid for up to 7 days. Noted explicitly as a known limitation rather than hidden.

**Amended at task 0.5:** there is no logout endpoint and no revocation list. Logging out is `localStorage.removeItem` in the browser; the token itself remains valid until `exp`. This follows from the decision above rather than extending it — a revocation list is server-side session state, which is precisely what a stateless JWT was chosen to avoid — and it is written down here so the omission reads as deliberate rather than forgotten.

## 012 — English only, i18n-ready

**Decision:** English UI, all strings keyed in `en.json`, CSS logical properties throughout.
**Alternative:** Ship bilingual English/Hebrew immediately.
**Reasoning:** RTL support done properly costs several days across every component. Structuring for it from day one costs nothing and turns "add Hebrew" into a new JSON file plus `dir="rtl"`.
**Trade-off accepted:** Not usable in Hebrew at submission. Explicitly a next step rather than an omission.

## 013 — A structured form, not a chat interface

**Decision:** Outfit requests go through a form — occasion chips, date, coat override, and a free-text notes field — extended by two structured interactions: anchoring on an item, and swapping a single item in a returned look.
**Alternative:** A conversational chat with the stylist, as some competing apps offer.
**Reasoning:** Three problems with chat. It demands typing at the exact moment the user has least patience — a weekday morning; three taps take four seconds, composing a sentence takes twenty. It is untestable: every turn is free-form input, which leaves no stable assertion and would undermine the entire QA story. And it requires carrying conversation history into every call, inflating the prompt and complicating validation. The two things a user actually wants that a plain form cannot express are *build around this specific garment* and *this one piece is wrong* — and both are better served by a structured field than by a sentence.
**Trade-off accepted:** Cannot handle open-ended requests like "something that makes me look taller". The free-text `notes` field absorbs most of that at no cost, since it is passed to the model verbatim.

## 014 — Per-item swap instead of full regeneration

**Decision:** Each item in a look card carries a ↻ that replaces only that item, keeping the rest locked.
**Alternative:** A single "Try again" that regenerates the whole look.
**Reasoning:** In practice a suggested look is usually acceptable with exactly one piece wrong — most often the shoes. Full regeneration discards the parts that worked and is the most commonly reported frustration with outfit apps. Per-item swap costs one extra request field and one validation rule, reuses the same endpoint entirely, and produces an unusually clean E2E assertion: every other item must be byte-identical.
**Trade-off accepted:** One API call per swap. At the observed usage rate this is negligible, and the rate limit already caps it.

## 015 — Angular 22, with Reactive Forms rather than Signal Forms

**Decision:** Angular 22 (stable since June 2026), standalone components, signals for state, zoneless change detection, and **Reactive Forms** for all form handling.
**Alternative considered (version):** Angular 19, which was the assumed version in an earlier draft of this plan. It reached end of life on 19 May 2026 — no security patches, no browser-compatibility updates. Starting a new project on an unsupported major is indefensible, so v22 it is.
**Alternative considered (forms):** Signal Forms, which reached stable status in v22 and are positioned as the future recommended API.
**Reasoning:** Reactive Forms are mature, thoroughly documented, and already familiar. Signal Forms are stable but new, which means fewer worked examples and a real chance of losing a day to an unfamiliar API — inside a six-week schedule that is a bad trade. Nothing in this project needs what Signal Forms add.
**Trade-off accepted:** The forms layer is not on the newest API. Reactive Forms remain fully supported and are not deprecated. Worth stating plainly in the defence: the newest option is not automatically the right one on a fixed deadline.
**Knock-on effects:** Zoneless is the v22 default and requires no changes here, since state was already signal-based. Angular's default unit-test runner is now Vitest rather than Karma; `ng test` is wired into CI. ~~Node 20+ is required.~~ **Corrected at task 0.8:** `@angular/cli@22.1.3` declares `node: ^22.22.3 || ^24.15.0 || >=26.0.0`, which excludes Node 20 outright. This project uses Node 24 LTS — see 054.

## 016 — Project name: Bijoux

**Decision:** The project is named **Bijoux**, tagline "AI wardrobe". Repository: `bijoux-wardrobe`.
**Alternative:** `Styla`, the working title used through planning.
**Reasoning:** Styla is already in use twice in adjacent territory — a fashion app of the same name serving curated shoppable outfits and saved closets, and a German e-commerce frontend vendor trading under styla.com since 2012. For a portfolio project the risk is not legal, it is that the name returns someone else's product when searched. The wardrobe-app category is also crowded with short invented English names (Whering, Indyx, Fits, Acloset, Pureple), so a French register reads as deliberately different rather than as one more entry in the list.
**Trade-off accepted:** *Bijoux* means jewellery, not clothing, so the name does not describe the product literally, and non-French speakers may misspell it. Both are mitigated by the tagline, which carries the descriptive load and always appears with the name in the README, the repository description, and the defence slides.

## 017 — Commits are written by hand, never by the agent

**Decision:** Claude Code is prohibited from running any git command that writes to the repository. It prints a suggested commit message at the end of each task; the developer stages and commits manually. Read-only git commands remain available to the agent.
**Alternative:** Let the agent commit at the end of each task, which is faster and keeps the working tree clean automatically.
**Reasoning:** A capstone is defended, not just submitted, and "who wrote this?" is a fair question. A commit history assembled by hand is a history whose author can walk through it line by line. Manual staging also forces a review pass over every diff before it is recorded, which catches agent drift far earlier than a stage-end review does.
**Trade-off accepted:** Slower, and the working tree needs manual attention. Read-only access is explicitly preserved so the agent can still run `git diff` to inspect its own changes — without it, the rule would degrade the agent's usefulness for no gain.

## 018 — Python 3.14, not 3.12

**Decision:** The backend targets Python 3.14. `ruff` runs with `target-version = "py314"` and `mypy` with `python_version = "3.14"`.
**Alternative:** Python 3.12, as named in the original stack table.
**Reasoning:** 3.14 is the current stable release. Starting a new project on an older minor buys nothing and shortens the support window before the code is even submitted. The cost of being current surfaced immediately as a broken dependency (see 019) — which is better discovered in week one than in Stage 5.
**Trade-off accepted:** A small number of libraries lag a new minor release. `passlib` was the only casualty here and it was replaceable in fifteen lines. `docs/README.md` and `CONVENTIONS.md` were corrected to match.

## 019 — bcrypt directly, not passlib

**Decision:** `requirements.txt` pins plain `bcrypt`. `core/security.py` calls it directly and caps password length itself.
**Alternative:** `passlib[bcrypt]`, as listed in STAGE-0 task 0.2's dependency list.
**Reasoning:** passlib is broken on Python 3.14 — it imports the stdlib `crypt` module, which was removed in 3.13. Separately, bcrypt 5 raises on inputs longer than 72 bytes where earlier versions silently truncated them. Calling bcrypt directly means the truncation is an explicit, visible decision in our code rather than behaviour inherited from a wrapper that has changed twice.
**Trade-off accepted:** We lose passlib's `CryptContext` — algorithm agility and rehash-on-verify. A single-algorithm project with one password hash needs neither. Task 0.5 owns capping password length at 72 bytes and must say so in the validation error rather than truncating silently.

## 020 — Tooling configuration in backend/pyproject.toml

**Decision:** `ruff` and `mypy` configuration live in `backend/pyproject.toml`.
**Alternative:** Separate `ruff.toml` and `mypy.ini`, or no configuration at all.
**Reasoning:** The definition of done requires lint and type checks to pass, so the configuration must exist and be committed. `pyproject.toml` is the file both tools discover without a flag, which means `ruff check` and `mypy` work with no arguments locally and in CI. No stage file owns this file, which is the only reason it needs an entry here.
**Trade-off accepted:** A committed file that no stage file mentions. Note the deliberate scope limit: `files = ["app"]` means `alembic/` and `tests/` are not type-checked. Migrations are historical scripts, not application code, and type-checking them would gate the build on generated boilerplate.

## 021 — Settings is a module-level singleton with UPPER_SNAKE fields

**Decision:** `settings = Settings()` at module scope in `core/config.py`, imported directly wherever it is needed. Fields are UPPER_SNAKE and match their environment variable names exactly; values derived from them are lowercase properties (`allowed_origins`, `is_production`). Only `DATABASE_URL` and `JWT_SECRET` are required.
**Alternative:** `@lru_cache`-decorated `get_settings()` injected with `Depends`, which is the pattern in FastAPI's own documentation.
**Reasoning:** Services in this project are plain functions, not route handlers (see CONVENTIONS), so they cannot receive a dependency — they import `settings`. Injecting it would mean threading a parameter through every service signature to solve a problem we do not have. UPPER_SNAKE because `06-TESTING-STRATEGY.md` already writes `settings.USE_FAKE_AI`, and because a field named identically to its environment variable removes a translation step when debugging a deployment at 2am.
**Trade-off accepted:** Settings cannot be swapped per-request via `dependency_overrides`. Tests set environment variables or monkeypatch attributes instead — which is what they would have to do for a service function in any case.

## 022 — SQLAlchemy used synchronously

**Decision:** Synchronous engine, `Session`, and `def` route handlers. psycopg 3 in sync mode.
**Alternative:** `asyncpg` with `AsyncSession` and `async def` throughout.
**Reasoning:** The workload is bounded by OpenAI latency, not by database throughput, and FastAPI runs sync handlers in a threadpool. Async would add `asyncpg`, async test fixtures and `greenlet` to the dependency tree, and complicate the integration layer that `06-TESTING-STRATEGY.md` builds on `TestClient` and a real Postgres. The AI service functions remain `async` because they are HTTP clients — that is unrelated to the database and is not evidence for an async ORM.
**Trade-off accepted:** A sync handler occupies a threadpool worker for the duration of its database calls. At demo scale this is invisible; at high concurrency it would not be, and that is the point at which the decision should be revisited.

## 023 — Three PostgreSQL enum types, not thirteen

**Decision:** `item_status`, `item_category` and `item_layer` are native PostgreSQL enum types. `subcategory`, `fit`, `length`, `rise`, `color_primary`, `color_secondary`, `pattern` and `material` are `TEXT`.
**Alternative:** A native enum type per attribute — the literal reading of "all enum types" in STAGE-0 task 0.3, since reworded.
**Reasoning:** The closed vocabulary is enforced in `app/enums.py` and at the AI boundary, where an invalid value becomes a validation failure and a retry (`03-AI-CONTRACTS.md`). A native enum converts that same event into a `DataError` raised in the write path, after the retry opportunity has already passed — the wrong layer for the error. PostgreSQL enum types are also close to immutable: a value can be added but not removed without recreating the type and rewriting every dependent column, and the colours, patterns, materials and subcategories are exactly the lists expected to move during Stages 1 and 2. The three that are native are structural rather than descriptive: `status` is set by the application, and all three are what `idx_items_wardrobe` and the layering rules key on. `subcategory` could not be a native enum in any case, because its validity depends on the parent `category`.
**Trade-off accepted:** Nothing at the database level rejects `color_primary = 'burgundy'`. Every write path must go through `validate_tag_dict`. That is a discipline rather than a guarantee, and it is stated as a known limitation rather than hidden.

## 024 — Enum types created and dropped with op.execute

**Decision:** Migration `0001` issues `CREATE TYPE` and `DROP TYPE` through `op.execute`. The `postgresql.ENUM` objects that type the columns carry `create_type=False`.
**Alternative:** `ENUM.create(op.get_bind())` and `.drop(op.get_bind())`, the pattern in Alembic's own cookbook.
**Reasoning:** `op.get_bind()` returns `None` in offline mode, so `.create()` raises and `alembic upgrade head --sql` cannot render the migration at all. `op.execute` behaves identically online and offline. `create_type=False` is separately load-bearing: without it SQLAlchemy auto-creates the type on `create_table` but never drops it, so `downgrade base` leaves orphaned types behind and the next `upgrade head` fails with `type "item_status" already exists`.
**Trade-off accepted:** The enum values appear twice in the migration — once in the `CREATE TYPE` string, once in the `ENUM` object. This is acceptable because a migration is a historical snapshot: it is never edited once applied, so drift from `app/enums.py` is expected and is resolved by a new migration rather than by keeping this file in sync.

## 025 — Migrations are hand-written, never autogenerated

**Decision:** Every migration is written by hand from the DDL in `02-DATA-MODEL.md`. `alembic revision --autogenerate` is not part of the workflow.
**Alternative:** Define the ORM models first and autogenerate each migration from them.
**Reasoning:** The schema uses `CITEXT`, a partial index and four `CHECK` constraints. Autogenerate reproduces none of them faithfully, so a generated file would need hand-editing into the same result by a longer route. Writing from the DDL also keeps `02-DATA-MODEL.md` as the source of truth rather than quietly promoting the models to that role.
**Trade-off accepted:** Models and migrations are kept in agreement by hand. The mitigation is the constraint naming convention pinned in `app/db/base.py`: migrations spell the resulting names out literally, so a schema built by `create_all` and one built by migrations are directly comparable. One trap to know about — `target_metadata` in `alembic/env.py` stays empty until models are imported there, so anyone running `--autogenerate` before that import exists will be offered a migration that drops both tables.

**Amended at task 0.5:** `User` has now landed and is imported, so the trap changes shape rather than closing. With a model for `users` and none for `items` until task 0.7, `--autogenerate` in that window offers a migration that drops `items` alone — quieter and considerably more plausible-looking than the original, which proposed dropping everything. Re-read this line when 0.7 adds the `Item` model, at which point it stops applying.

## 026 — No separate index on items.short_id

**Decision:** `short_id` carries a `UNIQUE` constraint and no additional index. `CREATE INDEX idx_items_short` was removed from `02-DATA-MODEL.md` and never shipped in `0001`.
**Alternative:** Keep it, as originally specified in the data model.
**Reasoning:** A `UNIQUE` constraint in PostgreSQL is implemented as a unique btree index on the same column. A second plain index on that column is an exact duplicate — identical structure, no query it can serve that the first cannot, and both maintained on every insert and update.
**Trade-off accepted:** None. This is redundancy removed. It is recorded only because the index was specified in the data model, and without this entry its absence would read as an omission rather than a decision.

## 027 — /health returns 200 when the database is unreachable

**Decision:** `GET /health` always returns 200. `status` reports the process and is always `"ok"`; `db` reports the dependency and is `"ok"` or `"error"`.
**Alternative:** 503 when the `SELECT 1` fails.
**Reasoning:** Render recycles an instance whose health check fails, and on the free tier a recycle costs a 30–50 second cold start stacked on top of whatever the original fault was. Neon's free tier autosuspends, so a transient database failure is an ordinary event rather than an emergency. Keeping the process alive and reporting the dependency's state in the body is more useful than killing the only component still able to answer the question. The two fields also answer two different questions — if `status` mirrored `db`, one of them would be redundant.
**Trade-off accepted:** An orchestrator that reads only status codes cannot distinguish a degraded instance from a healthy one. Nothing in this deployment does that. The response shape is fixed from Stage 0 so the frontend never sees the field's type move.

## 028 — Tag validation is split across two layers

**Decision:** `app/enums.py` owns `validate_tag_dict(d) -> TagValidation`, a pure function that returns a report — the corrected `tags` dict, a tuple of `errors`, a tuple of `coerced` — and never raises, never imports, never calls anything. `app/services/vision.py` owns `validate_tags()`, which interprets that report: one retry on `errors` using `TagValidation.reason`, `TaggingError` on the second failure, and the `confidence < 0.35` comparison against `settings`. Two boundaries follow from this. The tag dict keeps the model's field name `confidence` through validation; the rename to the `items.ai_confidence` column happens at persistence in task 1.3. And vocabulary membership is tested with `value not in Vocabulary.values()`, never `value not in SomeEnum` and never by catching `ValueError` from the enum constructor. Constructing a member — `Category(category)` — is permitted only *after* a `.values()` guard has established that it cannot raise, which is what `is_valid_subcategory` does; `SUBCATEGORIES` is typed `dict[Category, …]`, so indexing it with a bare `str` is a type error even though `StrEnum` makes it work at runtime.
**Alternative:** One `validate_tags()` owning both halves, which is how the behaviour table in `03-AI-CONTRACTS.md` reads at first glance, and the boolean-returning `validate_tag_dict(d)` named in STAGE-0 task 0.4.
**Reasoning:** That table mixes a judgement ("subcategory does not belong to category") with the response to it ("retry once"). A retry is a second OpenAI call, so one function would force `enums.py` to import the vision service and through it `settings` and the OpenAI client — while `06-TESTING-STRATEGY.md` requires the vocabulary to be unit-tested with no AI and no environment at all. The report shape also serves a second caller the table never mentions: `PATCH /items/{id}` runs the same validator (`04-API-SPEC.md`) but must return `422` exactly where the vision path silently coerces. Neither a boolean nor a raised exception can express two policies over one set of rules. Keeping the key named `confidence` until persistence means the validator's input is exactly the documented model schema, with the rename in one place instead of at every call site. The membership convention is defensive: `Enum.__contains__` changed behaviour in Python 3.12 and its handling of unhashable input is version-sensitive, whereas comparing against a `list` uses `==` and cannot raise on whatever JSON arrives in a hand-crafted PATCH body.
**Trade-off accepted:** Two function names for what the documents describe as one, so a reader grepping for `validate_tags` finds only half the logic. `03-AI-CONTRACTS.md` carries a sentence naming which layer owns which column of the table, and this entry is the other half of the answer.

**Superseded in two places at task 1.2b. The split above stands; two of the details in it do not, and they are struck here rather than left standing beside 086.**

- **`validate_tags()` is `async validate_tags(raw, image_url)`.** This entry put the retry in that function and then described it with no way to make a second call — a tag dict cannot say which photograph it came from. Every document printed the one-argument form; all of them are corrected.
- **"the `confidence < 0.35` comparison against `settings`" is not built, and no such setting exists.** 086 has the argument: both branches of the comparison produce `status='ready'`, so the branch could only set a flag nothing reads. The sentence should never have specified a mechanism — it named a `settings` field that had not been written, and three documents then cited it as though it had.

The rest of this entry is unchanged and still load-bearing: the report shape, the two callers, the `confidence` key surviving until persistence, and the `.values()` guard before constructing a member — which is exactly what makes `ItemTags` safe to build in 1.2b.

## 029 — `length` is one flat enum, not a per-category map

**Decision:** `Length` holds all eleven values in one vocabulary — sleeve lengths (`sleeveless`, `short_sleeve`, `long_sleeve`), top lengths (`crop`, `regular`, `longline`) and hem lengths (`mini`, `midi`, `maxi`, `ankle`, `full`). There is no `LENGTHS` mapping parallel to `SUBCATEGORIES`. `length: "maxi"` on a t-shirt validates.
**Alternative:** A per-category map, which is the treatment `subcategory` already gets for exactly the same reason.
**Reasoning:** The three axes do not collide in practice — the vision model does not offer `maxi` for a t-shirt — and `length` is advisory in the stylist prompt rather than load-bearing: nothing keys on it the way the layering rule keys on `layer`. A second category-dependent map would double the validation surface, the seed data's exposure to it, and the test matrix, to catch a class of error that has not been observed. An out-of-vocabulary `length` is coerced to null in any case, so the failure mode is a missing attribute rather than a wrong one.
**Trade-off accepted:** An impossible combination passes validation and reaches the database. Revisit if the Stage 1 golden-dataset run shows `length` errors concentrated on the wrong axis rather than spread across it.

**Amended before task 1.2 — the premise is falsified, in the neighbouring field, before the golden set exists.** This entry rests on the claim that "the three axes do not collide in practice — the vision model does not offer `maxi` for a t-shirt". Seven JPEGs through `tag_item` returned **`fit: "skinny"` on a tank top**: a legal member of a flat vocabulary, arriving beside a category it cannot describe. `maxi` on a t-shirt and `skinny` on a tank top are the same sentence, and the condition this entry set for revisiting — a golden-set run — turned out not to be necessary to observe it. The reasoning about **cost** is untouched and still stands: a per-category map doubles the validation surface and the test matrix. What has changed is that the risk it was weighed against is no longer hypothetical. `DECISIONS.md` 084 carries the general rule and 1.2 owns the decision for all three fields.

**Closed at task 1.2a, and closed by three things rather than one.** `02-DATA-MODEL.md`'s `length` section now carries per-category rules and no longer states that `maxi` on a t-shirt validates; `02`'s `fit` section carries the three narrowed words that answer the falsifying instance; and 085 has the mechanism both sit on. **`length` is no longer one flat enum** — the sleeve words apply to `top`/`dress`/`outerwear` and the hem words to `bottom`/`dress`/`outerwear`, so this entry's own example, `maxi` on a t-shirt, is now a coercion to null with a reason. `test_maxi_on_a_t_shirt_no_longer_validates` is that example as a test.

What survives of this entry is the **cost** argument, and it survives in a specific place: the middle five values — `crop`, `regular`, `longline`, `ankle`, `full` — are still unconstrained, because they describe more than one axis each and a rule over them would coerce correct answers away. So the flat list was not wrong everywhere; it was wrong at the two ends. The condition this entry set for revisiting — a golden-set run — is still worth honouring in the other direction: 1.11 should report whether the middle five ever land on the wrong axis, which is the only evidence that would justify narrowing them too.

## 030 — `PATCH /items/{id}` clears the category-dependent fields rather than demanding them

**Decision:** The route loads the item, merges the request body over it, and passes the merged dict to `validate_tag_dict`; any `errors` **or** any `coerced` entry is a `422` naming the offending field. When the body changes `category`, the route first clears the three fields whose validity depends on it — `subcategory`, `rise`, `layer` — for any of them the same request does not supply, and validates the result. The request schema sets `model_config = ConfigDict(extra="forbid")`, so an unknown key is a `422` from Pydantic before any of this runs.
**Alternative:** Require the client to send every dependent field a category change invalidates. For `bottom` → `top` that is `subcategory` **and** `rise: null`; for anything → `shoes` it is `subcategory` **and** `layer: "standalone"`.
**Reasoning:** Treating a coercion as a `422` is right when the client asked for something impossible and wrong when the *stored row* is what became impossible — and a category change is the second case. A stored `rise: "high"` and `layer: "base"` were valid until the category moved out from under them, and `validate_tag_dict` coerces both, so under the alternative even a well-formed request carrying a correct new subcategory returns `422`. The alternative also pushes the vocabulary's dependency rules into every client: the frontend would have to reimplement the vocabulary's standalone-category rule in TypeScript purely to construct a legal request. Clearing does that work once, on the server, from rules that already exist. It closes a gap in the other direction too — `outerwear` → `top` with a stored `layer: "outer"` triggers no coercion at all, so the alternative would leave a stale layer in place with no error at all. On extra keys: Pydantic's default is `extra="ignore"`, which would make `PATCH {"colour_primary": "navy"}` return `200` having changed nothing — a typo that reads as success. `validate_tag_dict` cannot catch it, since it only inspects keys it knows, so the schema is the only place it can be caught.
**Trade-off accepted:** `PATCH {"category": "top"}` on a pair of jeans returns `200` having silently nulled `subcategory`, `rise` **and** `layer`. That is real data loss on a success response, and it is the sharpest edge in this decision. It is accepted because the discarded values were already wrong the moment the category moved — a `subcategory` of `jeans` under category `top`, a `rise` on a garment that has none — and because the alternative returns `422` on a request that is otherwise correct. The mitigation is entirely in the UI: the tag editor in task 1.9 clears and re-prompts for all three selects — `subcategory`, `rise` and `layer`, not `subcategory` alone — the moment the category select changes, so the user sees three empty fields before saving rather than discovering them nulled afterwards. An API client that does not do this gets no warning, which is the honest limit of this decision.

**Amended at task 1.2a — it is five fields now, not three, and the list is no longer written down here.** `fit` and `length` gained per-category rules (085), so a stored `fit: "relaxed"` becomes impossible the moment the category moves to `shoes`, exactly as a stored `rise` already did. Under the unamended rule that would be a `422` on an otherwise correct request — the failure this entry exists to prevent, arriving through two new doors. The route therefore clears **`subcategory`, `rise`, `layer`, `fit` and `length`**, and it reads that list from `app/enums.py` as `CATEGORY_DEPENDENT_FIELDS` rather than restating it, so a field that gains a rule in the vocabulary cannot be forgotten in the route. `_STANDALONE_CATEGORIES`, named in the reasoning above through task 1.1, no longer exists: it is four rows of `LAYERS_BY_CATEGORY`.

**The trade-off widens with it, and the widening is not free.** `PATCH {"category": "dress"}` on a top now discards `fit` and `length` as well, and unlike `rise` on a non-bottom those two were often still valid — a `relaxed` top becoming a `relaxed` dress loses a correct value. That is the same shape of loss this entry already accepted for `layer`, one field further, and it is accepted for the same reason: the alternative returns `422` on a request that is otherwise correct. **Task 1.9's editor must therefore clear and re-prompt five selects, not three**, and the stage file says so.

## 031 — PyJWT, not python-jose

**Decision:** `requirements.txt` pins `PyJWT`. `core/security.py` calls `jwt.encode` and `jwt.decode` from it. `python-jose[cryptography]` is removed, and STAGE-0 task 0.2's dependency list is corrected to match.
**Alternative:** Keep `python-jose[cryptography]`, which is what task 0.2 named and what was already installed in the virtual environment.
**Reasoning:** `python-jose` was **not** broken. Verified on Python 3.14.5 before the swap: it encodes, decodes, and rejects a tampered signature correctly. This is therefore not a repeat of 019, where the library genuinely did not import. What `python-jose` does is pull in `ecdsa` as a hard dependency. That package is not side-channel resistant, its maintainers have stated that becoming so is out of scope for the project, and the Minerva timing advisory against it is consequently unfixed by design rather than pending a release. **This project never reaches that code. The only algorithm in use is HS256 — HMAC-SHA256, which involves no elliptic-curve arithmetic whatsoever — so the advisory was never reachable in our usage and swapping libraries fixed no live vulnerability.** The reason for the swap is narrower than that and is worth stating precisely: it removes an unmaintained transitive dependency the project does not use, from a tree that has to be defensible line by line. `PyJWT` is actively maintained, is what FastAPI's own security documentation now uses, and covers HS256 without dragging in `ecdsa`, `rsa` or `pyasn1`.
**Trade-off accepted:** A dependency change and a re-install for no functional gain — the tokens are byte-identical either way, and nothing about the auth flow changes. Accepted because "I removed a dependency I was not using" is a better answer under questioning than "it was already in the file", and because the distinction this entry exists to preserve is the one most easily blurred: **this was dependency hygiene, not a security fix.** Nothing in this project was ever vulnerable to the advisory in question, and claiming otherwise would be overstating the work.

## 032 — `EmailStr`, and what it does not guarantee

**Decision:** `email-validator` is added to `requirements.txt` and to task 0.2's dependency list. `RegisterRequest` and `LoginRequest` type `email` as Pydantic's `EmailStr`. Deliverability checking stays off, which is Pydantic's default, so validation is syntactic only.
**Alternative:** A plain `str` with a minimal check — a regex, or simply requiring an `@`.
**Reasoning:** `EmailStr` cannot be imported without `email-validator`; it raises `ImportError` at class-definition time. That makes the package's absence from 0.2's list a genuine gap in the plan rather than an untidy omission in `requirements.txt`. Hand-rolling the validation is a well-documented way to be subtly wrong forever: a minimal check accepts `a@`, and a regex thorough enough to be worth having is longer than the entire schema and still wrong at the edges. With a plain `str` the only other validation anywhere in the system would be the browser's `type="email"`, which any client can skip.
**Worth knowing before you write a test or a curl command:** `email-validator` rejects the RFC 2606 special-use domains — `.test`, `.invalid`, `.local` and `.localhost` all fail with "the part after the @-sign is a special-use or reserved name", *before* any deliverability question arises. `example.com`, `.example` and `bijoux.app` all pass, so `demo@bijoux.app` in task 1.10's seed script is safe. Use `example.com` for throwaway accounts.
**Trade-off accepted:** Syntactic validity is not existence. `nobody@example.com` registers successfully. There is no confirmation email in this project — deliberately, since it would require an SMTP provider, a token table and a second flow, for an application whose accounts are a demo login and the author's — and `04-API-SPEC.md` lists no password-reset endpoint either. The consequence is that a mistyped address produces an account that cannot be contacted and cannot be recovered. Recorded as a known limitation rather than mitigated.

## 033 — One `{detail, code}` envelope, including FastAPI's 422

**Decision:** `core/errors.py` defines `ApiError`, an `HTTPException` subclass carrying a stable `code`, plus two handlers registered on the app in `main.py`: one rendering `ApiError` as `{"detail": …, "code": …}`, and one reshaping Pydantic's `RequestValidationError` into those same two keys, with the offending field named inside the `detail` string. `CONVENTIONS.md`'s code list gains `email_exists`, `invalid_credentials`, `invalid_token` and `validation_error`.
The envelope covers every error the **application** raises, plus validation. It does not cover routing-level failures Starlette raises before any of our code runs — a `404` on an unknown path and a `405` on the wrong method return a bare `{"detail": "Not Found"}` with no `code`, and that is accepted rather than papered over: neither is an application error the frontend branches on, and giving them a code would mean inventing one that can only ever mean "you asked for something that does not exist".
**Alternative:** Wrap only our own errors and leave FastAPI's 422 in its native shape.
**Reasoning:** `CONVENTIONS.md` and `04-API-SPEC.md` both promise a single error envelope, and out of the box neither half of that promise holds: `HTTPException` produces a `detail` with no `code`, and `RequestValidationError` produces a `detail` that is a *list of dictionaries*. Task 0.5 is the first task in the project that can return an error at all — `/health` cannot fail by design (027) — so the choice is to build this now or let task 0.9's login screen branch on a shape that will move underneath it. The raw 422 body is also precisely what `CONVENTIONS.md` means by "the frontend never renders a raw error", and the register form is the first place a user would meet one. Naming the field inside `detail` rather than adding a third key keeps the envelope literally two keys everywhere, and satisfies both `04-API-SPEC.md`'s "`422` with the offending field" and 030's "a `422` **naming** the offending field" — both say *naming*, neither requires a separate key.
**Trade-off accepted:** A request that fails three field validations reports only the first. That is real information loss on every 422 in the project, including `PATCH /items/{id}` in task 1.4, and it is accepted knowingly rather than discovered later: the forms in this application are three fields wide, the frontend writes its own per-field messages in any case, and a `detail` that is sometimes a string and sometimes a list is worse for a client to consume than a message that is occasionally incomplete. If a wider form ever needs the full list, the place to add it is a third key on the 422 handler alone — never a change to the envelope itself.

## 034 — One `UserResponse` for the whole user resource

**Decision:** A single `UserResponse` — every column of `users` except `password_hash` — is returned by `POST /auth/register`, `POST /auth/login`, `GET /auth/me`, and by `PATCH /me` when Stage 2 builds it. It lives in `schemas/user.py`, separately from the register and login request bodies in `schemas/auth.py`.
**Alternative:** A minimal `{id, email, display_name}` for the auth endpoints now, widened at Stage 2 when the profile screen needs the rest.
**Reasoning:** `04-API-SPEC.md` writes `"user": { … }` three times and never expands it, and the shape freezes the moment task 0.9 reads it. Two shapes for one resource would mean the frontend holds a thin user object after login and a fat one after `PATCH /me`, with a merge between them and a window in which `style_notes` is `undefined` rather than `null` — a distinction that TypeScript will not save you from at three in the morning. Every profile column is nullable, so the wide version costs one line per field and no behaviour at all today. The file split exists so Stage 2's `me.py` can import the response model without also importing a register body it has no use for.
**Trade-off accepted:** Login and register responses carry ten mostly-null fields for a user who has not filled in a profile. Measured in bytes this is nothing, and the alternative trades those bytes for a class of merge bug.

## 035 — `HTTPBearer`, and 401 for everything `get_current_user` can see

**Decision:** `get_current_user` reads the credential through `HTTPBearer(auto_error=False)` and raises `401` with a `WWW-Authenticate: Bearer` header for every failure it can distinguish: no header at all, a malformed header, a bad signature, an expired token, and a well-formed token whose `sub` no longer resolves to a row.
**Alternative:** `OAuth2PasswordBearer(tokenUrl=…)`, which is the pattern in FastAPI's own tutorial; and, for the deleted-user case, a `404`.
**Reasoning:** `OAuth2PasswordBearer` declares a token endpoint that accepts form-encoded `username` and `password`. `04-API-SPEC.md` specifies a JSON body with `email`, so that declaration would be a lie told to every reader of `/docs`: Swagger's "Authorize" button would post the wrong content type with the wrong field names to `/auth/login` and fail, which is worse than having no button. `HTTPBearer` describes what this API actually does — a bearer token in a header — and its Swagger affordance works. On the deleted user: a `404` answers a question the caller did not ask. The caller presented a credential, and the credential is no longer good; that is a `401`, and it keeps the frontend's interceptor on one branch instead of two.
**Trade-off accepted:** No one-click login in `/docs` — a token must be pasted, which means calling `/auth/login` first. And collapsing five distinct failures into one status is deliberate rather than lazy: a client cannot tell an expired token from a forged one. That is the correct amount of information to hand an unauthenticated caller, and the distinction remains available in the logs, where it belongs.

## 036 — Passwords: minimum 8 characters, maximum 72 bytes, enforced in two places

**Decision:** `RegisterRequest` enforces `min_length=8` — characters, per `04-API-SPEC.md` — and a validator rejecting any password whose UTF-8 encoding exceeds 72 bytes, with a message that says *bytes*. `hash_password` repeats the byte check and raises `ValueError` independently of any schema. Nothing is ever truncated.
**Alternative:** Enforce the limit once, on the schema; or truncate at 72 bytes, the way `passlib` silently did before bcrypt 5.
**Reasoning:** Decision 019 assigned this to task 0.5 and required the cap to be stated rather than applied silently, because bcrypt 5 raises where earlier versions truncated. The check is duplicated because the schema is not the only entrance: `scripts/seed_demo.py` in task 1.10 calls `hash_password` directly, and without the second check it would surface bcrypt's own message about truncating manually instead of ours. **The two limits are counted in different units, and that is not an oversight — it is the detail in this task most likely to be mistaken for a bug six weeks from now.** The minimum is 8 *characters* because that is what the API spec states and what a user counts. The maximum is 72 *bytes* because that is bcrypt's actual boundary. For ASCII the two units coincide and nobody notices. For anything else they do not: Hebrew, Arabic, Cyrillic and Greek are two bytes per character in UTF-8, and emoji are four, so a 40-character Hebrew password is 80 bytes and is rejected — a password its owner would reasonably describe as "forty characters, well under your limit". The error message names bytes for exactly this reason, and this paragraph exists so the behaviour is discoverable from the documentation rather than only from a code comment.
**Trade-off accepted:** A limit users cannot compute in their heads, on a project whose stated next language is Hebrew (012). The mitigation is the wording of the message, not the rule — the rule is bcrypt's and cannot be moved without changing algorithm. The two constants live in different modules for the same reason they are counted in different units: `MAX_PASSWORD_BYTES` sits in `core/security.py` next to the library that imposes it and must hold for every caller including the seed script, while `MIN_PASSWORD_LENGTH` sits in `schemas/auth.py` because it is API policy from `04-API-SPEC.md` and means nothing to `hash_password`. The schema imports the byte limit rather than restating `72`.

## 037 — The email-enumeration oracle is in register, not login

**Decision:** `POST /auth/register` returns `409` with `code: "email_exists"`, detected by catching the `IntegrityError` raised by `uq_users_email` rather than by selecting on the email first. `POST /auth/login` returns the same `401` with the same message for an unknown email and for a wrong password, and — when the email is unknown — still performs a bcrypt comparison against a constant dummy hash before returning.
**Alternative:** For register, `SELECT` on the email and return `409` if a row comes back. For login, skip the dummy hash on the grounds that the message is already identical, which is all `04-API-SPEC.md` asks for.
**Reasoning:** Three separate points, all of which the alternative gets wrong in a different way. **Detection:** selecting before inserting reads more naturally but carries a TOCTOU window — two concurrent registrations both see no row, and the second one gets a `500` from the constraint instead of a `409`. Catching the violation is race-free in a single round-trip, and 025's naming convention is what makes it precise rather than a blanket catch: the exception identifies `uq_users_email` by name, so this cannot silently swallow some future constraint on the same table. **Timing:** the spec requires the same message for both login failures, but without the dummy hash the *timing* still separates them — an unknown email returns in about a millisecond, a known one after roughly 200 milliseconds of bcrypt. An identical message delivered in a reliably different duration is not an identical response. Three lines close the channel. **Honesty:** none of the above conceals which emails are registered, because `POST /auth/register` reports it directly, by design.
**Trade-off accepted:** The register endpoint is an email-enumeration oracle, and since `04-API-SPEC.md` lists no rate limit on `/auth/*`, it is an unthrottled one. The alternative — a generic "registration failed" — would make the single most common genuine error, *you already have an account*, unrecoverable from the interface. For an application of this scale that is the right side of the trade, and it is written down here rather than left to be found. Note what the login-side work still buys under that concession: enumeration through register is a deliberate, visible, individually loggable request to a known endpoint, whereas a timing channel on login is none of those three things.

## 038 — `security.py` knows nothing about users

**Decision:** `core/security.py` imports nothing from `app.models` or `app.db`. `create_access_token(subject: str)` takes a string, and the token payload is exactly `sub` — the user's UUID rendered as a string — plus `iat` and `exp`. `decode_access_token` returns the subject or raises. Resolving that subject to a row is `get_current_user`'s job, in `core/deps.py`.
**Alternative:** `create_access_token(user: User)`, carrying `email` and `display_name` as additional claims so `get_current_user` can skip the database lookup entirely.
**Reasoning:** This is the same discipline 028 draws around `enums.py`. A module that imports no ORM and no session can be unit-tested with no database, no fixtures and no environment, which is exactly what allows task 0.5 to ship tests before task 0.10 builds any scaffolding. On the extra claims: a token is not a cache. Embedding `email` and `display_name` would let a stale token render a name the user changed an hour ago, for as long as the seven days decision 011 grants it, and it would place a personal identifier in a string that lives in `localStorage`. The `sub` is the UUID rather than the email for that second reason, and it is a string because RFC 7519 requires `sub` to be one and libraries disagree about how strictly to enforce it.
**Trade-off accepted:** One `SELECT` on every authenticated request. At this scale that is a primary-key lookup on a connection the request is already holding, and it buys the property that a deleted or renamed user is reflected on the very next request rather than up to seven days later.

**Amended at task 0.5 — do not delete the `isinstance` guard in `decode_access_token` as dead code.** It is currently unreachable: PyJWT 2.13 validates `sub` on decode as well as on encode and raises `InvalidSubjectError` before our line runs, which is why no unit test reaches that branch. It stays for two reasons. It is what makes the `-> str` annotation true — `jwt.decode` returns `dict[str, Any]`, `mypy`'s `warn_return_any` is off, and without the check the function would quietly return `Any`. And PyJWT only added that `sub` validation in 2.10, while `requirements.txt` carries no version pin, so it is a behaviour this file cannot rely on. A guard whose necessity depends on an unpinned library's version is not a guard.

## 039 — Every request body forbids unknown fields

**Decision:** `RegisterRequest` and `LoginRequest` both set `model_config = ConfigDict(extra="forbid")`, so an unrecognised key is a `422` before the route body runs. Every request schema added from here on does the same.
**Alternative:** Pydantic's default, `extra="ignore"`, which silently discards unknown keys.
**Reasoning:** This generalises what 030 already established for `PATCH /items/{id}`, and the reasoning transfers unchanged: under `ignore`, `POST /auth/register` with `displayname` instead of `display_name` returns `201` having created an account with no display name, and the client is told nothing. A typo that reads as success is the most expensive kind, because there is no failure to investigate. Making it a rule for every schema rather than a special case for the one endpoint 030 named means nobody has to remember which bodies are strict.
**Trade-off accepted:** The API cannot be extended additively — a client sending a field that a newer version will understand is rejected today rather than ignored. For a project with exactly one client, written in the same repository, that costs nothing and buys an immediate error on every typo.

## 040 — `POST /auth/register` inserts first and reads back

**Decision:** The route builds the `User`, commits, and handles a duplicate email by catching `IntegrityError` and testing for `uq_users_email` in the driver's message; anything else re-raises untouched. After a successful commit it calls `db.refresh(user)` before serialising.
**Alternative:** `SELECT` on the email first and return `409` if a row exists (rejected in 037 for the TOCTOU race). For the identification, read psycopg's `exc.orig.diag.constraint_name` instead of matching the message text. For the refresh, rely on SQLAlchemy's `eager_defaults` to have fetched the server-generated columns during the flush.
**Reasoning:** On identification: `exc.orig.diag` is more precise than a substring match, but it is psycopg-specific and reaches through two layers of wrapping to get there. Matching on the constraint name works because 025 pinned that name — the string `uq_users_email` is not a guess about how PostgreSQL phrases errors, it is a name this project chose and spelled out in migration `0001`, and the `users` table has exactly one unique constraint. The narrow `if` matters more than which mechanism reads it: an `IntegrityError` that is *not* the email constraint must not be reported to the client as a duplicate email, so it re-raises and becomes a 500, which is the correct outcome for a constraint violation nobody anticipated. On the refresh: `id` comes back from the flush via `RETURNING`, but `created_at` is a server default that SQLAlchemy is not guaranteed to have fetched, and `UserResponse` requires it. An explicit `refresh` makes the read deliberate rather than dependent on `eager_defaults` behaviour that varies by version and dialect.
**Trade-off accepted:** One extra `SELECT` on registration, which happens once per user in the lifetime of an account. And a string match against a driver message, which is more fragile than reading a structured field — mitigated by the fact that the string is a name we control rather than wording the driver controls, and it is exactly what 025's naming convention exists to make possible.

**Corrected before task 1.1 — the sentence about the refresh was false, and `db.refresh(user)` is removed.** This entry claimed `created_at` "is a server default that SQLAlchemy is not guaranteed to have fetched". It is fetched. SQLAlchemy 2.0's ORM insert emits `RETURNING` for exactly the server-generated columns, measured against `postgres:18` inside a transaction that was rolled back:

```
users  RETURNING users.id, users.created_at
items  RETURNING items.id, items.status, items.water_resistant, items.attributes,
       items.user_edited, items.is_archived, items.created_at, items.updated_at
```

Reading `id` and `created_at` after `commit()` with the refresh omitted emits **zero** further statements, so the round trip this entry described as deliberate was simply redundant. `eager_defaults` is not what makes this work and is not involved.

The measurement was owed. 075 established the same thing for `Item` at 0.10 and deliberately left both in place, because removing one while the other stood on identical reasoning would have left the codebase less coherent than leaving both. `Item`'s result was not inherited here — `User` has a different column set and was measured separately, precisely because `created_at` is the column this entry names.

**What made this worth doing at all is the document, not the query.** One `SELECT` per registration is nothing. A persuasively written and false justification in a decision log is not: the next person to add a write path would have copied it, and 075 records that this is not hypothetical, since the sentence had already been copied into `items.py` once. `tests/integration/test_server_defaults.py` now asserts the `RETURNING` clause and that no `SELECT` follows the insert — a green suite proves nothing here, which 075 also established by measurement.

## 041 — Route return annotations are the response model

**Decision:** Route handlers declare their response type as an ordinary return annotation — `def login(...) -> TokenResponse` — and no route passes `response_model=`. `status_code=` is still passed where it is not 200.
**Alternative:** `@router.post("/login", response_model=TokenResponse)`, which is the form in most FastAPI material and in `04-API-SPEC.md`'s mental model.
**Reasoning:** FastAPI has inferred the response model from the return annotation since 0.89, and it validates and filters identically either way. Passing both states the same fact twice, in two places that can drift: a handler whose annotation says `UserResponse` and whose decorator says `TokenResponse` is legal Python and a lie in the OpenAPI schema. Using only the annotation also means `mypy` checks the thing the documentation is generated from, rather than checking one and publishing the other.
**Trade-off accepted:** Looks unfamiliar next to older FastAPI examples, and the response type is no longer visible on the decorator line where a reader skimming route registrations might look for it. Verified against the generated OpenAPI document rather than assumed.

## 042 — `except A, B:` is Python 3.14 syntax, not a typo

**Decision:** `core/deps.py` contains `except jwt.InvalidTokenError, ValueError:` without parentheses. This is PEP 758, new in Python 3.14, and it is what `ruff format` produces because `pyproject.toml` sets `target-version = "py314"`. Restoring the parentheses fails `ruff format --check`.
**Alternative:** Restructure to avoid catching two exception types at once — two sequential `try` blocks, each catching one — purely so the line does not resemble Python 2.
**Reasoning:** This entry exists because the line looks exactly like Python 2's `except E, name:`, which was removed in Python 3.0, so a reader's first instinct is that it cannot possibly run. It does; it was verified importing on 3.14.5 before being committed. The two exceptions are genuinely one concept — the credential could not be turned into a user id, whether because the token was invalid or because its subject was not a UUID — and splitting them into two `try` blocks to avoid an unfamiliar spelling would make the code worse to satisfy a formatting habit. Fighting the formatter to preserve the look of an older Python is the wrong instinct on a project that deliberately targets the current one (018).
**Trade-off accepted:** A line that reads as a syntax error to anyone who last wrote Python before 3.14, in a file that will be read under questioning. The mitigation is this entry: the answer is "PEP 758, and ruff formats it that way because we target 3.14".

## 043 — Four error codes added at task 0.6, one of which closes a gap 033 left open

**Decision:** `CONVENTIONS.md`'s code list gains `unsupported_file_type` (`415`), `file_too_large` (`413`), `not_found` (`404`) and `upload_failed` (`502`). The first two are raised by task 0.7's upload route from the exceptions `services/storage.py` defines; `not_found` is 0.7's answer for an item that exists but belongs to another user; `upload_failed` is any failure to store an image.
**Alternative:** For the `404`, one code per resource — `item_not_found` now, `look_not_found` at Stage 2, `trip_not_found` at Stage 4. For `upload_failed`, nothing: let a Cloudinary failure surface as an unhandled exception, since no document asks for a code.
**Reasoning:** On the `404`: a code exists so the frontend can branch on it, and the frontend already knows which endpoint it called. The resource name in the code carries no information the caller lacks, so three codes would be three ways to say one thing. On `upload_failed`: nothing in `04-API-SPEC.md`, `STAGE-0` or `06-TESTING-STRATEGY.md` names a failure code for the upload path, and that absence is a gap rather than a decision. An unhandled exception produces Starlette's bare `500` — no `code` key at all, which is the single shape `CONVENTIONS.md` promises the frontend never sees, on the one screen where a user has just handed the application twenty photographs. Decision 033's carve-out does not cover it: that exempts routing-level `404` and `405` raised *before* our code runs, and this is our code failing. `502` rather than `500` because the fault is a third party's, which is the same reasoning that gave `stylist_failed` a `502`.
**Trade-off accepted:** `not_found` cannot distinguish "this item never existed" from "this item is not yours", which is deliberate and is the entire point — `06-TESTING-STRATEGY.md` requires cross-user isolation, and an API that answers those two questions differently is an existence oracle for other people's wardrobes. The cost is that a genuine client bug and a genuine authorisation failure look identical in the browser, and are separable only in the server logs.

## 044 — `storage.py` raises its own exceptions, and catches more than Cloudinary's

**Decision:** `services/storage.py` defines `UnsupportedFileTypeError`, `FileTooLargeError` and `StorageError` and raises those. It imports nothing from FastAPI. Task 0.7's route maps them onto `ApiError` with the codes in 043. `upload_image` wraps the Cloudinary call in two handlers: `except cloudinary.exceptions.Error` for the expected failure, and `except Exception` for everything else, which logs `type(exc).__name__` and raises the same `StorageError`.
**Alternative:** Raise `ApiError` directly from the service, which needs no mapping layer at all. And catch only `cloudinary.exceptions.Error`, which is what the SDK documents itself as raising.
**Reasoning:** `ApiError` subclasses `HTTPException`, so a service that raises it can only be called from inside a request — and `scripts/seed_demo.py` at task 1.10 calls `upload_image` from a command line, where a `413` is meaningless. This is the same argument decision 036 already settled for `hash_password`, and `vision.py`'s `TaggingError` at 1.2 is the same shape again. On the second handler: `except Exception` is normally exactly what `CONVENTIONS.md` forbids, and it is here because the narrow version was measured and found insufficient. `cloudinary.utils.sign_request` raises a plain `ValueError("Must supply api_key")` — and `cloudinary_api_url` a plain `ValueError("Must supply cloud_name")` — *before* any request is made, so with a blank credential all three escape `except cloudinary.exceptions.Error` untouched:

```
no cloud_name  ESCAPED as builtins.ValueError: Must supply cloud_name
no api_key     ESCAPED as builtins.ValueError: Must supply api_key
no api_secret  ESCAPED as builtins.ValueError: Must supply api_secret
```

A code invented to guarantee that the frontend never meets a bare `500` is worth nothing if the commonest deployment mistake — an unset key — is the one case that produces one. Network failures, by contrast, *are* wrapped: an unresolvable host raises `cloudinary.exceptions.Error` and was already caught. The two handlers are kept separate rather than collapsed into one so that the expected failure is still caught by name, and so the log distinguishes "Cloudinary rejected an upload" from "Cloudinary upload failed unexpectedly".
**Trade-off accepted:** The wide handler will also swallow a genuine programming error — a `TypeError` from a bad call — and report it to the user as a storage failure. Mitigated rather than solved: the exception is chained with `from exc` so the traceback survives, and the type is logged, so the distinction is available where it belongs. The narrower rule in `CONVENTIONS.md` still stands everywhere else; this is a trust boundary with a third-party SDK, and the exception is recorded here rather than left as a file that quietly disagrees with the convention.

## 045 — The accepted file type is decided from the bytes, and the list is narrower than `image/*`

**Decision:** `validate_image(file_bytes)` accepts JPEG, PNG, WebP and HEIC/HEIF, identified by their signatures — JPEG and PNG at offset 0, `RIFF`/`WEBP` at 0 and 8, `ftyp` plus an HEIF brand at 4 and 8. The multipart part's declared `Content-Type` is never consulted. Type is checked before size, so an over-large non-image reports the type. The limit is `MAX_UPLOAD_MB * 1024 * 1024` — mebibytes. `04-API-SPEC.md`'s "`image/*` only" and `01-ARCHITECTURE.md`'s "reject non-image MIME types" were corrected to match.
**Alternative:** Take the declared `Content-Type` as a parameter and check it starts with `image/`, which is what both documents said and what STAGE-0's "validate MIME type" most naturally means.
**Reasoning:** The declared type is client-controlled. A `.txt` renamed and declared `image/jpeg` passes a header check, reaches Cloudinary, and comes back as a rejected upload — a `500` where the spec promises a `415`. Reading a signature is about fifteen lines and needs no dependency: Python removed `imghdr` in 3.13, and `python-magic` would add a system library to the deployment. It also keeps STAGE-0's documented `upload_image(file_bytes, user_id)` signature exactly as written, since no MIME parameter has to be threaded in, and it makes the whole rule a pure function of bytes — unit-testable from byte literals with no HTTP, no Cloudinary and no fixture, which is the property decisions 028 and 038 bought for `enums.py` and `security.py`. On the narrowing: `image/*` admits `image/svg+xml`, an XML document that can carry script and that Cloudinary would store and serve; it also admits GIF, BMP and TIFF, none of which are garment photographs. A signature table *is* an allow-list, so both problems have one answer. HEIC is on the list deliberately: this is a mobile-first application whose primary input is `capture="environment"`, and an iPhone set to keep originals uploads HEIF rather than JPEG. Every comparison is a slice rather than an index — `data[4:8]`, never `data[7]` — so a file shorter than a signature yields a short slice that matches nothing instead of raising `IndexError` on the truncated upload that a dropped connection produces. Mebibytes because the number has to be stated somewhere and the frontend mirror at 0.8 has to agree with it; `settings.max_upload_bytes` is where both sides read it.
**Trade-off accepted:** A genuine JPEG that a client mislabels `text/plain` is accepted, which is the exact opposite of what "validate MIME type" implies — the honest description of this rule is that we do not validate the MIME type at all, we validate the bytes. Accepted because the bytes are the thing that matters and the header is the thing that lies. Separately, the allow-list will reject a format some future phone produces (AVIF is the obvious candidate) with a message that lists four formats and no way for the user to know theirs was close; adding one is one line and one test, and doing it deliberately is the point.

## 046 — `Transform` lives in `storage.py`, and `build_url` formats the URL itself

**Decision:** The four transform names are a `StrEnum` in `services/storage.py`, mapped to their transformation strings by a module-level dict. `build_url` builds `https://res.cloudinary.com/{cloud}/image/upload/{transform}/{quote(public_id)}` with an f-string, and raises `StorageError` when `CLOUDINARY_CLOUD_NAME` is empty.
**Alternative:** Put `Transform` in `app/enums.py`, which `01-ARCHITECTURE.md` calls "THE closed vocabulary — single source of truth". And build the URL with the SDK's own `cloudinary.utils.cloudinary_url`.
**Reasoning:** `02-DATA-MODEL.md` is authoritative over `enums.py` and says "do not add fields or enum values that are not listed here". A delivery transform is not a garment attribute, is not in the data model, and is never stored in a column. `enums.ts` is a hand-mirror of `enums.py`, so putting transforms there would oblige the frontend mirror to carry names it does not want — what `cloudinary-url.pipe.ts` needs is the transformation *strings*. On the builder: `cloudinary_url` was tried and rejected on measurement, not on taste. It returns a `(url, options)` **tuple**; it inserts a `/v1/` version segment that `version=False` does not suppress; and it emits `http://` unless `secure=True` is configured, which on an HTTPS frontend is mixed content that the browser blocks outright. Against three surprises, the frontend pipe will hand-format the same URL in TypeScript regardless, and two builders that must agree byte for byte are better as two obvious f-strings than as one f-string and one library. The `public_id` is passed through `quote`, whose default `safe="/"` preserves the folder separators and escapes anything else that would change the meaning of the path. The empty-cloud-name guard is the one `cloudinary_url` behaviour worth keeping: without it the function returns a URL with an empty host segment and the failure surfaces as a broken image days later.
**Worth knowing before you write a test:** the two functions read their configuration at different times, and this will cost an hour if it is not known in advance. `build_url` reads `settings.CLOUDINARY_CLOUD_NAME` on every call, so `monkeypatch.setattr(settings, "CLOUDINARY_CLOUD_NAME", …)` works — the tests rely on it. `upload_image` does not: `cloudinary.config()` runs once at import and copies the credentials into the SDK's global singleton, so monkeypatching `settings.CLOUDINARY_API_KEY` afterwards changes nothing. Measured:

```
configured api_key at import : 'k'
settings after mutation      : 'changed-after-import'
configured api_key after     : 'k'
```

To change a credential in a test, call `cloudinary.config(api_key=…)` or monkeypatch `cloudinary.uploader.upload` outright, which is what `test_storage.py` does.
**Settled at task 1.1 — the HEIC question below is closed, and the two entries no longer hold the same string.** `f_auto` did *not* fall back to HEIC; measured three ways, it returned `image/jpeg` with no `Accept` header and with `*/*`, and `image/webp` to a browser-like one. `vision` is pinned to `f_jpg` anyway, because the header OpenAI's fetcher sends is not observable and format negotiation has no upside for a machine consumer. `DECISIONS.md` 083 has the measurement and is careful about what it does and does not claim.

**Trade-off accepted:** Two entries in the transform table, `detail` and `vision`, hold identical strings today, which reads as duplication. They are two entries so the vision transform can move when task 1.11's golden-set run says the model wants something different, without changing what a person sees on the item screen. Also unresolved at 0.6 and owned by task 1.1: `f_auto` on a **HEIC** original, delivered to a client that sends no `Accept` header, is not confirmed to produce a browser-renderable format — Cloudinary documents the fallback as "the format specified by the file extension", and these URLs deliberately carry no extension. It matters because the `vision` URL is fetched by OpenAI, not by a browser. If it fails, the fix is `f_jpg` on the `vision` transform alone.

## 047 — One Cloudinary folder per user, and the media is world-readable

**Decision:** `upload_image` uploads into `{CLOUDINARY_UPLOAD_FOLDER}/{user_id}` and lets Cloudinary generate the `public_id`, so a stored id looks like `bijoux/<user uuid>/vbqoj4on69txdjzvhgw6`. Assets are ordinary public Cloudinary images. Delivery URLs are unsigned and never expire.
**Alternative:** A flat folder; or a `public_id` we generate ourselves. And, for delivery, `type: "authenticated"` with every URL signed by the backend.
**Reasoning:** A flat folder makes "which of these assets belong to a user who no longer exists?" unanswerable without the database, and orphaned assets are a real category here — task 0.7 uploads before it inserts the row, so a failed insert leaves one behind, and every developer who runs 0.6's exercise commands creates one under a `user_id` that will never exist. Foldering by user makes that audit a directory listing. Generating the id ourselves would be natural if it were the item's UUID, but `01-ARCHITECTURE.md`'s flow uploads at step 3 and inserts the row at step 4, so there is no item id yet. On signing: `07-DEPLOYMENT.md` designs for the browser building its own transform URLs from the cloud name — that is what `cloudinary-url.pipe.ts` is — and a signed URL cannot be built in the browser. Signing would mean the backend hydrating and re-signing a URL for every item in every response.
**Trade-off accepted:** `06-TESTING-STRATEGY.md` requires cross-user isolation on every item endpoint, and that isolation stops at the API. Anyone holding a `public_id` can fetch that garment photograph directly from Cloudinary, forever, with no token. The `public_id`s are unguessable and are only ever disclosed to their owner, so this is a "a leaked URL stays valid" limitation of the same shape as 011's seven-day token, not an enumerable one — but it is a limitation, and a wardrobe is more personal than most media. Recorded rather than mitigated. Note also that the `public_id` embeds the owner's UUID, which `04-API-SPEC.md` already puts in URLs.

## 048 — Every file is decided before any file is uploaded, in two passes over twelve bytes

**Decision:** `POST /items/upload` validates the whole batch before it uploads anything, in two passes that read almost nothing. Pass one reads `storage.SIGNATURE_BYTES` — twelve — from each part, seeks back, and calls the new public `validate_image_type`; the first failure is a `415`. Pass two compares each part's `UploadFile.size` against `settings.max_upload_bytes` and reads nothing at all; the first failure is a `413`. Only when both passes clear does the route read a file in full, upload it, discard the bytes, and move to the next. `validate_image` is unchanged in behaviour and now calls `validate_image_type` for its type half. More than `MAX_FILES_PER_REQUEST` parts is a `422` `validation_error` from `File(min_length=1, max_length=…)`, naming `files` inside `detail` — no new error code.
**Alternative:** Read all twenty files into memory, call `validate_image` on each, then upload each — which is what 0.6's note ("the validator is public and separate so that 0.7 can check all twenty files before uploading any") most naturally describes. Or validate and upload file by file, which needs no pre-pass at all.
**Reasoning:** The two requirements STAGE-0 sets for this task pull against each other, and the twelve-byte signature is what reconciles them. `04-API-SPEC.md` rejects the whole request for one bad file, so validating as you upload would strand the assets of files one through six when file seven fails — the alternative is not merely untidy, it manufactures the orphans 047 exists to make auditable. But reading twenty files in full to type-check them puts up to 200 MB in RAM, which is the thing 008 claimed was bounded and was not. A type check needs twelve bytes, not a file: `data[8:12]` is the widest offset any accepted signature reads, for WebP and HEIF alike. So the batch is fully decided for 240 bytes of reading, and the full read happens once per file with the previous file's bytes already released. **Type before size, deliberately**, because 045 established that an over-large non-image reports its type, and a size-first ordering would have silently inverted that rule the moment a batch was involved. Within a pass, the first failing file in request order is the one reported, which is the same information loss 033 already accepted for a multi-field `422`. On the file count: `File(max_length=…)` produces a `422` before the handler runs and reuses `validation_error`, where a new `too_many_files` code would be a fifth addition to a list that grew by four at 0.6 and would say nothing the `detail` does not.
**Trade-off accepted:** Three real residuals, none of them free. **First**, a file whose first three bytes are `\xff\xd8\xff` but which is otherwise not a JPEG passes both passes, passes `validate_image`, and is rejected by Cloudinary — surfacing as `502` `upload_failed` rather than `415`. That is 0.6's rule unchanged, not a regression, and closing it would mean decoding the image. **Second**, `UploadFile.size` is typed `int | None`, and the route skips the size check when it is `None`. Measured: Starlette constructs every part as `UploadFile(size=0, …)` and increments on write, so `None` is unreachable for a parsed request. If a future parser made it reachable, the consequence is that the memory bound is lost while the limit is not — `validate_image` still raises `FileTooLargeError` after the read and the client still gets a `413`. That is exactly the second-line-of-defence role 0.6 gave the validator, and it is why the branch is permissive rather than fatal. **Third**, none of this bounds what arrives off the wire; see the amendment to 008.

## 049 — The upload route is a synchronous `def`, and STAGE-0's wording was wrong

**Decision:** `upload_items` and both `GET` handlers are plain `def`, so FastAPI runs them in its anyio threadpool. Bytes are read with `file.file.read(…)` and `file.file.seek(0)` rather than `await file.read(…)`. STAGE-0 task 0.7's instruction "Check `UploadFile.size` before `await file.read()`" is corrected to "before the bytes are read"; the substance is untouched.
**Alternative:** `async def` with `await file.read()`, which is what the stage file literally said and what most FastAPI upload examples show.
**Reasoning:** The Cloudinary SDK is synchronous and takes one to two seconds per file. In an `async def` handler that call blocks the event loop for the whole batch — twenty to forty seconds on a full request — during which every other request in the process is stalled. On Render's free tier that is one instance, so it stalls the application. Fixing it inside an async handler means wrapping the upload in `run_in_threadpool`, and the synchronous `Session` in another, at which point the handler is async in name and threaded in fact. `CONVENTIONS.md` already draws this line: "`async def` is for HTTP clients (OpenAI, Open-Meteo), not for database work", and this route is a database write with one blocking third-party call. A `def` handler puts the whole thing in one threadpool worker and needs no wrapping. `UploadFile.read` is itself `run_in_threadpool(self.file.read, …)` when the part has rolled to disk, so reaching for `.file` inside an already-threaded handler is what the async method would have done anyway.
**Trade-off accepted:** A long batch occupies one of anyio's forty default threadpool slots for its whole duration, so forty concurrent twenty-file uploads would saturate it. That is strictly better than the async version, where a single batch blocks *everything* rather than one slot, and it is far beyond this application's load. Separately, `.file.read()` is a slightly lower-level call than the documented async API, and a reader who knows FastAPI's upload examples will notice. The stage file is corrected rather than quietly disobeyed, because an instruction that survives in the documentation while the code does the opposite is worse than either.

## 050 — One `ItemResponse`, and `image_url` is computed rather than stored

**Decision:** A single `ItemResponse` — every column of `items`, plus a computed `image_url` — is returned by `POST /items/upload`, `GET /items` and `GET /items/{id}`, and will be returned by 1.4's `PATCH` and Stage 2's hydrated looks. Tag fields are `null` on a fresh row. `image_url` is a Pydantic `computed_field` derived from `image_public_id` with `Transform.THUMBNAIL`; `image_public_id` is on the response too. `04-API-SPEC.md`'s five-key 202 example is corrected: the body is a superset of what it printed.
**Alternative:** A narrow upload response carrying exactly the five keys the spec prints, widened later. And building `image_url` in each route rather than on the schema.
**Reasoning:** 034 settled this shape of question for `UserResponse` and the reasoning transfers without change: two shapes for one resource means the frontend holds a thin item after upload and a fat one after `GET`, with a merge between them and a window where `warmth` is `undefined` rather than `null`. Every tag column is nullable, so the wide version costs one line per field and no behaviour. On the transform: `thumbnail` is `w_300,h_300,c_pad,b_white`, which is exactly the wardrobe grid tile that 1.6's upload sheet renders the moment this response lands — nothing else the 202 could feed wants 800px. On carrying `image_public_id` as well: `02-DATA-MODEL.md` stores an id rather than a URL precisely so the transform is chosen at read time, and `05-FRONTEND-SPEC.md` ships `cloudinary-url.pipe.ts` to do that in the browser. A response with only a baked thumbnail URL leaves that pipe nothing to work from and the item detail screen at 1.9 no route to the `detail` transform. On computing rather than passing: a derived field cannot disagree with its source, and 1.4 and Stage 2 get it without remembering to.
**Trade-off accepted:** Two consequences worth naming. **The `public_id` embeds the owner's UUID** (047), which is safe today because the field is only ever returned to its owner, but it constrains any future share-link or public-look feature — that feature would be handing out a user id along with the photograph. Recorded, not designed around. **And `build_url` raises `StorageError` when `CLOUDINARY_CLOUD_NAME` is empty**, which on a `GET` happens during serialisation, after the handler has returned: the result is a bare `500` with no `code`, the one shape 043 says the frontend never sees. It is unreachable on `POST`, where an unset cloud name fails earlier inside `upload_image` (044's measured `ValueError`), but it is genuinely reachable on `GET /items` against a misconfigured deployment. Left as a `500` because a missing credential is a deployment fault rather than an application error, and because the alternative — emitting a URL with an empty host — is what 046 already rejected. `/health` does not check Cloudinary, so nothing surfaces it earlier; that is noted in `07-DEPLOYMENT.md`.

## 051 — All eleven documented query parameters, and what implementing them does not fix

**Decision:** `GET /items` implements every parameter `04-API-SPEC.md` lists — `status`, `category`, `color_primary`, `formality_min`, `formality_max`, `warmth_min`, `warmth_max`, `search`, `include_archived`, `limit`, `offset` — rather than the subset with a named consumer. `status`, `category` and `color_primary` are typed as the closed vocabulary, so a value outside it is a `422` naming the field. Archived rows are excluded unless `include_archived` is passed. Ordering is `created_at DESC, short_id`.
**Alternative:** Implement only `status` (1.7's polling), `include_archived`, `limit` and `offset`, since `05-FRONTEND-SPEC.md` filters client-side and the other five have no consumer before Stage 2 — which is what STAGE-0's "basic filtering" licenses and what `CONVENTIONS.md`'s ban on speculative work suggests.
**Reasoning:** FastAPI ignores query parameters it does not declare. Under the alternative, `GET /items?formality_min=3` returns `200` with an unfiltered list and tells the caller nothing — the typo-that-reads-as-success failure that 039 made a project-wide rule to prevent, arriving through the one door 039 does not cover. Since these parameters are already specified rather than invented, building them is implementing the contract, not future-proofing. The closed-vocabulary types are free correctness: `?status=almost_ready` is a `422` from Pydantic before the query is built. The `short_id` tiebreak in the ordering is not decoration — PostgreSQL's `now()` is the transaction timestamp, so all twenty rows of one upload share a `created_at` to the microsecond and pagination without a second key can repeat or drop rows between pages.
**Trade-off accepted:** Implementing all eleven closes "documented but unimplemented". It does **not** close the underlying gap, and saying otherwise would overstate it: a misspelled or entirely undocumented parameter — `?formalitymin=3`, `?colour_primary=navy` — is still silently ignored and still returns `200` with an unfiltered list. Query strings have no `extra="forbid"` equivalent, so 039's guarantee genuinely stops at request bodies. Closing it means rejecting unknown query keys in middleware, which is nobody's task today; it is recorded in `04-API-SPEC.md` with Stage 5's QA task named as its owner rather than left implied. Separately, `search` passes the user's string straight into `ILIKE '%…%'` without escaping `%` or `_`, so a search for `%` matches everything. That is the "simple `ILIKE`" the spec asks for and the query is parameterised, so it is a surprising result rather than an injection.

## 052 — `short_id` lives in `core/`, and a collision is a constraint violation rather than a `SELECT`

**Decision:** `generate_short_id()` and the alphabet live in `app/core/short_id.py`, importing nothing. The upload route generates ids for the whole batch, inserts, and handles a collision by catching `IntegrityError`, testing for `uq_items_short_id`, rolling back, regenerating **every** id and re-adding the rows. Three attempts; the third failure propagates as a `500`. An `IntegrityError` that does not name `uq_items_short_id` re-raises untouched.
**Alternative:** `SELECT` the existing `short_id`s and avoid them. Put the generator on `models/item.py` or in `services/`. And retry only the colliding row.
**Reasoning:** Selecting first carries the TOCTOU window 037 rejected for `uq_users_email`: two concurrent batches both see no row, and the second gets a `500` from the constraint instead of a retry. Catching the violation is race-free in one round trip, and 025's pinned constraint names are what make the catch narrow enough to be honest — the `if` names a constraint this project chose, so a future unique index on `items` cannot be silently reported as a `short_id` collision. The retry regenerates the whole batch rather than one row because a failed flush leaves the `Session` unusable: the only correct continuation is `rollback`, fresh objects, fresh commit, and per-row precision would buy nothing at 31⁶ ≈ 8.9×10⁸. On the location: the module imports no ORM and no session, which is the property 038 bought for `security.py` and 028 for `enums.py` — it is unit-testable with no fixture, and 1.10's seed script can import it from a command line without dragging in a model. `01-ARCHITECTURE.md` does not list it under `core/`, but that list is already illustrative rather than exhaustive: `core/logging.py` has existed since 0.2 and is not on it either. Both are now.
**Trade-off accepted:** `06-TESTING-STRATEGY.md` lists "`short_id` generation — … collision retry" among the unit tests that need no database, and the retry cannot be tested there: the thing that *detects* a collision is a `UNIQUE` constraint, so the behaviour is integration-shaped by construction. Task 0.7 ships the part that is genuinely pure — alphabet, length, exclusion of `0O1IL`, no repeat in a thousand draws — and the retry is a deferral with a named owner, task 0.10, on the same terms `CONVENTIONS.md` set for 0.5's route tests. The document is corrected rather than the test faked. Also accepted: three attempts is a bound with no evidence behind the number. At this alphabet and this wardrobe size a single collision is a one-in-ten-million event; three consecutive ones would mean the generator is broken, and a `500` is the right answer to that.

## 053 — A failed batch leaves its assets in Cloudinary, and logs them

**Decision:** Uploads happen before the rows are written, and the whole batch is one transaction committed once at the end. When a batch fails after at least one asset has been stored — a Cloudinary error on file seven, or any `SQLAlchemyError` from the insert — the route logs at `ERROR` with the `user_id` and the list of stranded `public_id`s, then lets the failure become its status. Nothing is deleted from Cloudinary.
**Alternative:** Call `cloudinary.uploader.destroy` on the already-uploaded assets before returning the error. Or commit per file, so a mid-batch failure at least keeps the rows that succeeded.
**Reasoning:** A compensating delete is new `storage.py` surface outside 0.6's scope and it introduces the failure it is meant to fix — the cleanup call can fail too, on exactly the outage that caused the original error, and now the handler has two exceptions and no good answer. 047 anticipated this case in as many words ("task 0.7 uploads before it inserts the row, so a failed insert leaves one behind") and chose per-user foldering as the mitigation. But a folder is only an audit trail if something writes down *which* assets were abandoned and when; a directory listing alone cannot distinguish a stranded asset from a live one without the database. The log line is what makes 047's claim true, and it costs nothing. On the single commit: committing per file would return `502` on a request that had already persisted six rows, which is partial success reported as failure — worse for a client to reason about than an orphaned asset is for us.
**Trade-off accepted:** Cloudinary accumulates assets that no row references, and only a person reading the logs will ever reconcile them. On a free tier with 25 monthly credits this is affordable; on a paid plan it would be a cost leak with no automatic cleanup. The reconciliation is a directory listing per user against `SELECT image_public_id FROM items WHERE user_id = …`, which is the audit 047 promised — it is now possible, not automatic, and no task in the plan performs it.

## 054 — Node 24, and the range three documents got wrong

**Decision:** The frontend toolchain runs on Node 24 LTS. `07-DEPLOYMENT.md`'s Vercel step and `DECISIONS.md` 015 are corrected from "Node 20 or newer" to Angular 22's actual declared range.
**Alternative:** Node 20, as both documents said; or Node 26, the other supported line.
**Reasoning:** `@angular/cli@22.1.3` declares `node: ^22.22.3 || ^24.15.0 || >=26.0.0`, and the CLI refuses to run outside it. **Node 20 is excluded**, so the instruction as written could never have worked — this is a documentation error found by reading the published `engines` field rather than by trusting the plan. The machine this was built on was on v25.6.0, which falls in the gap between `^24.15.0` and `>=26.0.0`: odd-numbered majors never enter LTS and Angular's range skips them deliberately. 24 over 26 because 24 is the current LTS line and Vercel's Node selector offers it.
**Trade-off accepted:** A second runtime version to keep track of, since the backend pins Python 3.14 separately, and a CI matrix that must name 24 explicitly rather than "latest". Cheap next to a scaffold command that cannot run.

## 055 — Scaffolded with `--directory`, so the project is `bijoux` and the folder is `frontend`

**Decision:** `ng new bijoux --directory frontend --style=scss --ssr=false --zoneless --skip-git`, run from the repository root into the existing empty `frontend/`.
**Alternative:** Scaffold `bijoux/` in a scratch directory and move its contents into `frontend/` — which is what was planned, on the belief that `--directory` had been removed from the CLI.
**Reasoning:** `--directory` is present and undeprecated in `@schematics/angular@22.1.3/ng-new/schema.json`. The plan's three-step move existed only to work around a flag that was assumed gone; checking the published schema replaced it with one command. The split matters because two documents disagree about the name: `01-ARCHITECTURE.md` puts the application at `frontend/`, while `07-DEPLOYMENT.md` pins Vercel's build output to `dist/bijoux/browser`. Both are satisfiable at once — the *project* is `bijoux`, the *directory* is `frontend`. `--skip-git` because we are already inside a repository. `--ssr=false` is passed because SSR is the one option here that prompts; `--zoneless` and `--routing` are both already the schematic defaults and are passed (or omitted) for legibility rather than effect.
**Trade-off accepted:** `angular.json` names a project that does not match its folder, which will briefly confuse anyone who opens the repository expecting them to agree. The alternative is renaming one of them and contradicting a document.

## 056 — Tailwind 4, wired the way Angular's own schematic wires it

**Decision:** Tailwind 4 (`tailwindcss` ^4.1.12, `@tailwindcss/postcss`, `postcss`, all devDependencies), configured CSS-first. A **separate plain-CSS file**, `src/tailwind.css`, holds `@import 'tailwindcss'` and the `@theme` block, and is listed *before* `src/styles.scss` in `angular.json`'s `styles` array. There is no `tailwind.config.js`.
**Alternative:** Pin Tailwind 3 and use a JavaScript config. Or put `@import "tailwindcss"` directly into `src/styles.scss`. Or rename `styles.scss` to `styles.css`.
**Reasoning:** On the version: pinning a new project to a superseded major is the worse trade, and v4's `@theme` block means the palette is declared once and generates its own utilities, with no second list to keep in sync. On the wiring: Sass resolves `@import` itself, before PostCSS ever runs, so `@import "tailwindcss"` inside a `.scss` file is a Sass module lookup that fails. The rename would have worked but throws away SCSS for component styles, which the stage file asks for. **The two-file arrangement is not invented here — it is exactly what Angular 22's own internal `tailwind` schematic does**: read `@schematics/angular@22.1.3/tailwind/index.js` and it looks for a `.css` file in the `styles` array, finds none in an SCSS project, creates `src/tailwind.css`, and prepends it. That schematic is marked `hidden` and `private`, so it cannot be invoked as `ng generate tailwind` — it runs only from `ng new --style=tailwind`, which would force CSS component styles. So the steps are performed by hand, copied from the implementation rather than guessed.
**Trade-off accepted:** Two global stylesheets where most projects have one, and a reader has to know why. And the real cost of v4: nearly all Tailwind material online is v3-shaped — `tailwind.config.js`, `theme.extend`, `@apply` conventions — so answers found by search will need translating, and "the config file the tutorial edits does not exist" is the expected first symptom. Recorded as a known consequence rather than discovered later.

## 057 — The accent is ink-blue, and the display face is deferred

**Decision:** The palette is `--color-canvas: #FAFAF8`, `--color-surface: #FFFFFF`, `--color-ink: #1A1A1A`, `--color-accent: #2F4858`. The display face is Fraunces, declared as `--font-display` with a `ui-serif, Georgia, serif` fallback. Body text uses Tailwind's default `--font-sans`, which is already a system stack, and is deliberately not overridden. **Self-hosting Fraunces is task 0.9's.**
**Alternative:** A muted terracotta `#B4654A` for the accent, and shipping the font files at 0.8.
**Reasoning:** `05-FRONTEND-SPEC.md` specified three of the four colours and named no accent and no typeface, so both were open. The accent is a deep desaturated blue because of the one rule the whole visual direction rests on — *the clothes are the design*. An accent is used on buttons, focus rings and chips, which sit directly beside garment photographs in the grid; terracotta is a warm mid-chroma colour that reads as a garment itself and competes with browns, beiges, reds and pinks, which are four of the seventeen wardrobe colours. `#2F4858` is dark enough to read as structure rather than as an object, and it contrasts adequately against both `#FAFAF8` and white. The font is deferred because self-hosting means woff2 files, an `@font-face` block, a preload hint and a decision about display swap — none of which changes any component's markup, all of which is better done once real headings exist. 0.9 owns it because 0.9 is the first task that renders type a user will judge.
**Trade-off accepted:** Between 0.8 and 0.9 every heading falls through to Georgia, so the application looks unfinished in exactly the way a screenshot taken now would show. Accepted because the fallback chain means nothing breaks, only the face changes.

**Amended at task 0.9 — a fifth colour, `--color-danger: #7f2f3c`.** The palette had no error colour, so validation messages and failure notices were distinguished by weight and position alone. That satisfies "never by colour alone" and it reads as a layout quirk rather than a problem. The value is a deep cool-leaning wine — blue channel above green, so it sits with `#2f4858` instead of pulling against it — at 8.46:1 on canvas against the accent's 9.18:1, so the two carry the same visual weight. Warmer bricks were rejected for 057's own reason: this token does not stay on forms, it is what task 1.3's failed tiles use, and those sit directly beside garment photographs. **The asymmetry is asserted, not just described**, because two adjacent paragraphs where one carries the class and one does not reads as an oversight to anyone tidying: `login.page.spec.ts` asserts the presence on one notice and the absence on the other. **It is applied only where something is wrong.** The `'unreachable'` notice does not take it, because that notice appears mostly while a sleeping instance wakes, its own text reassures ("You may still be signed in"), and a signal that means both "this failed" and "this is slow" leaves a user unable to tell a slow upload from a rejected one at 1.3.

## 058 — An `I18nService` we own, not a translation library

**Decision:** `core/i18n/i18n.service.ts` — roughly forty lines, signal-based, no dependency. It fetches `public/i18n/en.json` once through `provideAppInitializer`, holds a flat `Record<string, string>` in a signal, and exposes `t(key, params?)` with `{{name}}` interpolation. Components inject it and call `t()` in the template; there is no translate pipe.
**Alternative:** `@ngx-translate/core` v18, the standard runtime-JSON choice. Or Angular's built-in `@angular/localize`.
**Reasoning:** `@angular/localize` was never a candidate once the documents specified a JSON file — it is `$localize` plus XLIFF resolved at build time, one bundle per locale, and it does not read runtime JSON at all. Against ngx-translate the argument is proportion: this project ships one language, and 012 already decided Hebrew is a next step rather than a deliverable. A dependency that has to be defended, upgraded across an Angular major, and explained, in exchange for interpolation and a pipe, is not worth it at this size. **ngx-translate is the named escape hatch** — if a second locale actually arrives, swapping a forty-line service for it is a mechanical change at the call sites, because `t(key, params)` is the same shape as its `instant(key, params)`. Three internal choices worth naming. **Flat dotted keys**, so lookup is one property access rather than a tree walk. **No pipe**, because `05-FRONTEND-SPEC.md`'s `shared/pipes/` lists exactly two files and neither is this; injecting the service costs one line per component and adds nothing to the documented structure. **A failed load rejects and the application does not bootstrap** — the alternative renders every label as its own key, which is not a working application either, and a hard failure puts a missing build asset where a developer sees it.
**Trade-off accepted:** Code we maintain instead of code someone else maintains, including the interpolation regex and its edge cases. And the failure mode is a blank screen if `en.json` is missing from the deployed build — deliberate, but it is the harshest failure in the frontend and it is worth knowing before debugging a white page on Vercel.

## 059 — Types that describe an API payload keep the server's `snake_case`

**Decision:** `User`, `TokenResponse`, and every model added later that mirrors a response body use the field names the API sends — `display_name`, `home_lat`, `created_at`. Everything the frontend owns stays `camelCase`. `CONVENTIONS.md` is amended to say so.
**Alternative:** `camelCase` throughout, with a mapping layer converting each payload on arrival.
**Reasoning:** `CONVENTIONS.md`'s TypeScript rule says `camelCase` for "everything else", which taken literally makes every API model wrong. The mapping alternative is real work on every model — `item.model.ts` at 1.4 has twenty fields — and it gives every field two names, so a stack trace, a network tab and a source file disagree about what the thing is called. `04-API-SPEC.md` is authoritative over the wire shape, and a type whose job is to describe that shape should look like it. The boundary is legible: if the name came from the server, it is the server's name.
**Trade-off accepted:** Two naming conventions in one language, and the seam between them is a convention rather than anything the compiler enforces. `created_at` is also typed `string` rather than `Date`, because JSON has no date type and nothing parses it yet — a consumer that wants a `Date` constructs one.

## 060 — The interceptor skips two paths, not the `/auth/` prefix

**Decision:** `jwtInterceptor` attaches the bearer token to requests whose URL starts with `environment.apiUrl`, except `/auth/login` and `/auth/register`, which it names individually.
**Alternative:** Skip the whole `/auth/` prefix, which is the natural reading of `04-API-SPEC.md`'s "auth is required on everything except `/auth/*` and `/health`", and which is what this task was originally instructed to build.
**Reasoning:** `/auth/*` is not one group. `backend/app/api/v1/routes/auth.py` guards `me` with `Depends(get_current_user)`, so **`GET /auth/me` is bearer-authenticated** and a prefix skip breaks it permanently — every call returns `401` with no way for a client to fix it. The spec's sentence is describing which endpoints a caller can reach anonymously, not a prefix to strip a header from, and `/auth/me` is on the prefix while not being anonymous. The route file was read rather than the sentence trusted. The `apiUrl` restriction is the other half: without it the token would ride along on the `/i18n/en.json` fetch and on any third-party request the application ever makes.
**Trade-off accepted:** A hand-maintained list of two paths, which someone must remember to extend if a genuinely anonymous endpoint is ever added — a password reset would be the candidate, and `04-API-SPEC.md` lists none. A prefix rule needs no maintenance and is wrong; this needs a line and is right. The list is stated in the file as the reason, not just the rule.

## 061 — Native `src/environments`, and `NG_APP_API_URL` was never real

**Decision:** Configuration lives in `src/environments/environment.ts` (the base, production) and `environment.development.ts` (swapped in by `fileReplacements`), both typed against a shared `Environment` interface. The `NG_APP_API_URL` instruction is deleted from `07-DEPLOYMENT.md`.
**Alternative:** Add `@ngx-env/builder`, which is the package that gives `NG_APP_*` variables meaning.
**Reasoning:** `07-DEPLOYMENT.md` contradicted itself — one section specified `src/environments/`, another told Vercel to set `NG_APP_API_URL`. Plain Angular has no build-time environment-variable substitution, so that variable would have been set, ignored, and never noticed until the deployed build called `localhost`. One of the two had to go, and the one that requires no dependency is the one that stays. The shared interface exists because `fileReplacements` swaps whole files: without it, a key present in one file and missing from the other is an error only in whichever configuration is built, so the drift can ship. Typing both makes it a compile error in both.
**Trade-off accepted:** Changing the API URL for a deployment means editing a committed TypeScript file and pushing, not flipping a dashboard variable — worse operationally, and written into `07-DEPLOYMENT.md` so nobody looks for the setting. Note also that unlike `backend/.env`, these files **are** committed: the Cloudinary cloud name belongs there and is public by design (047), an API key never does.

## 062 — `currentUser` is not restored on reload at 0.8

**Decision:** `AuthService` reads the token from `localStorage` at construction; `currentUser` is populated only by a login or register in the current session. After a page reload the user is authenticated and `currentUser()` is `null`. **Task 0.9 owns the fix**, together with the global `401` handling deferred to it.
**Alternative:** Call `GET /auth/me` at bootstrap when a stored token exists. Or persist the user object in `localStorage` alongside the token.
**Reasoning:** Nothing at 0.8 reads `currentUser` — the guard needs only the token — so building either version now would be a method with no caller. Persisting the object is the one to avoid on principle rather than on scope: 038 already rejected putting `email` and `display_name` in the token because "a token is not a cache", and a copy in `localStorage` has the identical staleness problem with the same seven-day window. The bootstrap `/auth/me` call is the right answer, and it belongs with 0.9 because it is inseparable from the question 0.9 already owns — what to do when a stored token turns out to be bad. Two deferrals landing on one task is better than one task shipping half an answer.
**Trade-off accepted:** Between 0.8 and 0.9 there is a genuine inconsistency in the service: `isAuthenticated()` can be `true` while `currentUser()` is `null`, and any consumer written in that window would have to handle it. Nothing consumes it in that window, which is why the gap is affordable — but it is a real trap if 1.5 is built before 0.9, and it is named here so that ordering is a choice rather than an accident.

## 063 — The token lives in `localStorage`, and that is an XSS exposure we are accepting

**Decision:** `AuthService` persists the access token in `localStorage` under the key `bijoux.token`, reads it at construction, and removes it on logout. Nothing else is persisted.
**Alternative:** Hold the token in a signal only, so it dies with the tab. Or have the backend set it as an `httpOnly; Secure; SameSite=Strict` cookie.
**Reasoning:** In-memory only makes every page reload a logout. `/wardrobe` is the default route, 1.7 polls there while items tag, and a reload during a twenty-file upload is ordinary rather than exceptional — a session that cannot survive F5 is not usable. `sessionStorage` is not a middle ground: it carries exactly the same exposure and only shortens the window, so it buys the reload problem back without fixing the thing that matters. The cookie is the genuinely more secure option and it is not reachable from the frontend: `04-API-SPEC.md` specifies a bearer token in the `Authorization` header, 035 chose `HTTPBearer` over any cookie or form flow, and 011 chose a stateless JWT with no logout endpoint and no revocation list. Moving to cookies means a CSRF strategy, an endpoint that can clear the cookie, and `allow_credentials=True` on CORS — three changes across two documents and the backend, to protect a demo account and the author's.
**State the exposure plainly:** `localStorage` is readable by any JavaScript executing on the origin. **A single XSS anywhere in this application hands an attacker a token that is valid for up to seven days (011) and that nothing can revoke (011's amendment).** An `httpOnly` cookie would not be readable by that script. This is a real reduction in security and not a wash, and it is the strongest argument that could be made against the frontend's design.
**Trade-off accepted:** The mitigations are narrow and worth naming without overstating them. Angular escapes interpolated values by default, this project renders no user-supplied HTML and calls no `bypassSecurityTrust*`, and the closed vocabulary (005) means almost nothing a user types is ever displayed back — `display_name` and `style_notes` are the only free-text fields in the data model. That lowers the *likelihood* of an XSS; it does nothing about the *consequence*, which stays total. Recorded as a known limitation of the same family as 011's seven-day window and 047's permanently valid media URLs: a credential that remains good for its full lifetime once it leaks. If this application ever held a stranger's wardrobe, the cookie route is where to start, and it is a backend change first.

## 064 — `@theme static`, because Tailwind cannot see across a stylesheet boundary

**Decision:** The `@theme` block in `frontend/src/tailwind.css` carries the `static` modifier, so every palette token is emitted whether or not Tailwind believes it is used. A comment in the file states why, because the word has no visible effect and reads as noise.
**Alternative:** Plain `@theme`, which is what every Tailwind 4 example shows and what this project shipped for one round before the bug was found.
**Reasoning:** Tailwind 4 tree-shakes theme variables down to those referenced by CSS it emitted. That is invisible until something depends on a token Tailwind cannot see — and this project has exactly such a dependency from its first commit. `src/styles.scss` sets the page ground with `var(--color-canvas)` and `var(--color-ink)`, and `@angular/build` hands PostCSS **one stylesheet at a time**: `compileString` passes `from: filename` per file (`stylesheet-plugin-factory.js:247`). Tailwind processing `tailwind.css` is therefore structurally incapable of seeing a `var()` in `styles.scss`. Measured at task 0.8 with plain `@theme`: the built bundle contained preflight and exactly six theme variables — Tailwind's own `--font-sans`, `--font-mono` and four `--default-*`, which are precisely the ones preflight itself references — and none of ours. **The failure is silent.** The build succeeds, no warning is emitted, the page renders, and the background is simply white instead of `#FAFAF8`.
**Worth recording precisely, because the diagnosis was wrong before it was right.** Running the same file through the same Tailwind install outside the builder kept all four tokens, so the pruning could never be reproduced outside Angular's pipeline and the step responsible was never isolated. `static` is correct on its own merits regardless of which step prunes: **a design token consumed across a file boundary must not depend on a scanner inferring its usage.** Two other things were disproved along the way and are worth not re-testing: the PostCSS configuration was always being found (`postcss-configuration.js` accepts `postcss.config.json` and `.postcssrc.json`, searched in `[projectRoot, workspaceRoot]`, both of which are `frontend/` here), and `@tailwindcss/postcss@4.3.3` passes Angular's plugin guard (`typeof plugin === 'function' && plugin.postcss === true`), which throws rather than degrading when it fails.
**Trade-off accepted:** Every declared token ships whether or not anything uses it, so the palette can never shrink the bundle by going unused. At four tokens that is tens of bytes. The real cost is legibility: `static` is one word with no observable effect, in a file that works without it right up until it doesn't, which is the exact shape of thing a later reader deletes while tidying. The comment in `tailwind.css` and this entry are the whole mitigation.

## 065 — Fraunces is self-hosted at one subset, and the `opsz` axis earns its 30 KB

**Decision:** `public/fonts/fraunces-latin-variable.woff2`, 67,388 bytes, taken from the Google Fonts `css2` endpoint's **latin** block and committed alongside `OFL.txt`. `@font-face` declares `font-weight: 100 900`, `font-display: swap`, and the subset's own `unicode-range`. Nothing declares `opsz`.
**Alternative:** `@fontsource-variable/fraunces` as an npm dependency; two static weights; or a `wght`-only request at 36,560 bytes.
**Reasoning:** The package was rejected because the preload hint needs a stable known URL, which a file inside `node_modules` does not have without extra copying — a dependency *and* a build step to serve one file, in a project that declined a dependency for the whole i18n layer (058). On the axes, the file was read rather than the URL trusted: its `fvar` carries `opsz 9–144` and `wght 100–900`, so **Google's own `font-weight: 400 700` describes the request, not the file**, and copying it would silently clamp anything heavier. The `opsz` question was decided by measurement. A `wght`-only request is 46% smaller but pins optical size at **9**, the axis's small-text end, for headings rendered at 24–48px. The only other instance Google serves is `opsz@144` at 33,600 bytes — confirmed by that file's own `name` table reading `Fraunces 144pt` — which is the poster end. Arbitrary pins are refused: `opsz@30` returns the full variable file byte for byte. So the 30,828 bytes buy the *correct* optical size at the rendered size via `font-optical-sizing: auto`, which is the CSS initial value and needs no declaration; writing `font-variation-settings` would switch that automatic behaviour off.
**Trade-off accepted:** A 66 KB binary in git with no version marker, updated by re-running a documented command. And the preload is unconditional while `unicode-range` is not, so a page of purely non-Latin text would still fetch a font it cannot use — unreachable while the UI is English-only (012).

## 066 — The boot marker, and the only hard-coded user-facing string in the application

**Decision:** `index.html` carries a wordmark inside `<app-root>`, styled by an inline `<style>` block, with a second line — *"This is taking longer than usual. The server may be waking up."* — revealed at ten seconds by a CSS animation delay. Angular removes the host element's children when the root component renders, so nothing clears it manually.
**Alternative:** A blank page until bootstrap completes, which is what 0.8 shipped.
**Reasoning:** Blocking bootstrap on `GET /auth/me` (067) means a returning user waits, and on Render's free tier a cold start is 30–50 seconds of white screen. The marker makes that wait legible. **It does not shorten it.** The ten-second line exists to protect what the blank page gave for free: 058 made a missing `en.json` a hard bootstrap failure, and a blank page sends a developer to the console within seconds where a calm branded page does not. The wording hedges deliberately — the line has to be true both when an instance is waking (the common case) and when bootstrap is broken (the case it exists for), so it says *may*. **This is the one user-facing string not routed through `I18nService`**, and it cannot be: that service is loaded by an app initializer, so nothing before bootstrap can read a string from it. `role="status"` was tried and removed — a live region should be in the accessibility tree before its content changes, and `visibility: hidden` removes it, so whether a screen reader announces is implementation-specific. An unverifiable guarantee is worse than none.
**Trade-off accepted:** A user-facing surface no test covers and no component owns, and a bootstrap failure that now looks like patience rather than breakage for its first ten seconds. The inline `<style>` must stay inline — Angular defers the real stylesheet (`media="print"`), so a rule that waited on it would start the timer late — and it is the only such exception; everything else goes in `styles.scss` or Tailwind classes.

## 067 — `isAuthenticated` is a confirmed user, and `restoreNotice` has one writer per outcome

**Decision:** `isAuthenticated = computed(() => currentUser() !== null)`, populated by a `GET /auth/me` that **blocks bootstrap** via `provideAppInitializer` and always resolves. `restoreNotice` is `'unreachable' | 'signed-out' | null`. `logout()` does not touch it; `rejectSession()` clears the session and sets `'signed-out'`; `restore()` sets `'unreachable'` only when the failure is not a `401`.
**Alternative:** Keep `isAuthenticated` as a token check; make the restore non-blocking; use a `serverUnreachable` boolean.
**Reasoning:** This closes 062, which the token check did not. Blocking alone was not enough: with a stored token and an unreachable server the initializer resolves, a network failure must not clear the token, and `isAuthenticated()` would be `true` with `currentUser()` null — 062 through a different door, and routine on a free tier. Reading the **user** makes the invariant hold by construction, and it costs nothing at the login and register paths because `POST /auth/login` returns the user object in the same response (`_issue()` in `auth.py`); no second round trip. The notice exists because the unreachable user otherwise lands on a bare login form that silently claims they are signed out, and is a union rather than two booleans because the two states can never both be true. **The single-writer rule is the part worth keeping:** an earlier design had `logout()` clear the notice and `restore()` set it, which worked only because the interceptor happened to call `logout()` first — nothing stated that dependency and no test would have caught its reversal.
**The delay is defended by a test, not a comment.** `app.config.spec.ts` carries one assertion that the fake backend replies asynchronously, so removing `delay(0)` fails a named test instead of quietly weakening four — a comment only reaches a reader already looking at the line, and the person who breaks this is running a green suite and tidying.

**What the evidence for this actually is, because the first version of it was worthless.** `app.config.spec.ts` replaces `HttpBackend` outright, and with a synchronous reply every assertion in it passed *whether or not the initializer was awaited* — verified by dropping the `return` from `app.config.ts` and watching all 69 tests stay green. The fake now replies on a macrotask (`delay(0)`), and the same mutation fails the success-path test. A test for a blocking behaviour has to be slower than the thing it is testing, or it is only asserting the outcome.

**Trade-off accepted:** A returning user waits for `/auth/me` before anything renders, worst case a Render cold start (mitigated, not fixed, by 066). `token() !== null` with `isAuthenticated() === false` becomes a legitimate state meaning "a credential we hold but could not verify", which reads like a bug. And **`authenticated ⟹ notice is null` holds by construction rather than by assertion** — every path to a non-null `currentUser` runs through `accept()` or a successful `restore()`, both of which clear it — so the sign-out button deliberately carries no clearing line.

## 068 — The `401` branch redirects only after the router has navigated

**Decision:** `jwtInterceptor` catches `401` on authenticated API requests, calls `auth.rejectSession()`, and navigates to `/login` **only when `router.navigated` is true**. Both injections happen in the interceptor body, never inside `catchError`. The error is rethrown.
**Alternative:** Navigate unconditionally; or gate on a flag `restore()` holds; or omit the navigate entirely.
**Reasoning:** Three measured facts. **The navigate is redundant at bootstrap** — clearing the token is enough, because `authGuard` then rejects and lands the user on `/login` unaided. **It is destructive at bootstrap** — a navigation requested during an app initializer sets `navigationId`, and `Router.initialNavigation()` skips syncing to the browser URL when `hasRequestedNavigation` is true, so an expired-token deep link to `/register` was thrown away and the user landed on `/login` having asked for something else. **And it is the only thing that works mid-session** — a guard does not re-run on a route that is already active, so without it a `401` while the user sits on `/wardrobe` clears their session and moves nothing. `router.navigated` states that condition exactly, where a flag on `AuthService` would be a proxy that diverges at the retry button. This holds because the app uses plain `provideRouter(routes)`, where initial navigation runs from an `APP_BOOTSTRAP_LISTENER` after every initializer; **adding `withEnabledBlockingInitialNavigation()` sets `INITIAL_NAVIGATION` to 0 and moves it into an initializer**, at which point the outcome depends on provider order and this stops being reliable.
**On the wildcard, at task 0.9's request.** `{ path: '**', redirectTo: 'wardrobe' }` is kept, and `redirectTo: ''` was measured rather than reasoned about: it lands on `/` and **does not chain through** the empty-path route, so every mistyped URL would reach a blank page. The duplicated destination is the lesser cost. What the wildcard does not solve is the case that actually arrives at 1.9 — a stale or shared link to a deleted or someone else's item matches `/wardrobe/:id` perfectly and fails at the API with a `404`, where no route configuration is involved at all. **A not-found surface is owed at 1.9**, covering both an unknown route and a known route naming a resource that is gone, and it belongs with the `returnUrl` work above.

**Trade-off accepted:** The gate preserves deep links to **public routes only** — today `/login` and `/register`, and nothing else. A deep link to any guarded route still loses its URL, because `authGuard` rejects it regardless. The fix for that is a `returnUrl` on the guard, deliberately **not** built here: `/wardrobe` is the only guarded route and it is already the post-login destination, so the parameter could hold only the value it replaced. **Task 1.9 owns it**, as the first task shipping a guarded route that is not the default. And the mid-session case that justifies the navigate is itself unreachable until **1.7** starts polling — the test guards a future caller, and says so.

## 069 — `guestGuard` ships as a second export, not a fourth file

**Decision:** `core/auth/auth.guard.ts` exports both `authGuard` and `guestGuard`; `/login` and `/register` carry the latter.
**Alternative:** A `guest.guard.ts` beside it, or a redirect inside the two page components.
**Reasoning:** `05-FRONTEND-SPEC.md` names exactly three files under `core/auth/`, and the argument used at 060 to keep the skip list honest applies here too — a fourth file would put the code and the document back out of step over a twenty-line function. The two guards are exact inverses and document each other better adjacent than apart. Against the in-page redirect: a guard stops the component being constructed at all, where a redirect builds the `FormGroup`, injects `I18nService`, renders, and then navigates away.
**Trade-off accepted:** Someone searching for `guest.guard.ts` by filename will not find it. And `guestGuard` is only correct *because* the restore blocks (067) — under a non-blocking restore it could bounce a user to `/wardrobe` on a token that turned out to be dead a moment later.

## 070 — The auth forms mirror the API's rules, including the ones it states in bytes

**Decision:** Register requires a display name via a trim-aware validator, and its password field carries `minLength(8)` plus a `TextEncoder`-based 72-**byte** check. Login carries neither length rule. Both forms are `novalidate`, use no native `required`, and disable submit only while a request is in flight.
**Alternative:** Let the server's `422` carry it; add native constraint attributes; disable submit while the form is invalid.
**Reasoning:** `novalidate` is load-bearing rather than tidy: `type="email"` triggers native constraint validation, which blocks submission before Angular sees it and shows an unstyled, untranslatable bubble that preempts the i18n messages `CONVENTIONS.md` requires. Angular does not add `novalidate` for you, and jsdom enforces the same rule — so without it the test agrees with the browser that nothing happened, and both are wrong together. The trim-aware validator exists because `Validators.required` treats `"   "` as present and so does the API. Login gets no length rules because `LoginRequest` has none, and telling someone their existing password is too short explains nothing. Submit stays enabled on an invalid form so that submitting is possible at all — a disabled button gives a user nothing to act on, and leaves no way to assert that an invalid submit sends no request.
**Two things in these files that look arbitrary and are not.** The identifier field carries `autocomplete="username"` rather than `email`, because password managers pair `username` with `current-password`/`new-password` to offer save and fill; `email` is the token for an address that is *not* the account identifier, and here it is. Register's name field is `nickname`, not `name`, because the column is a display name rather than a legal one. And **no field carries a native `required`** — validation is `Validators.required` with `aria-required` for the accessible name, because a native attribute would hand submission back to the browser's constraint validation, which is what `novalidate` exists to prevent.

**A correction to this entry's own evidence.** It was claimed that jsdom enforces the same constraint validation as a browser, so a missing `novalidate` would fail a test. That is false for the specs as written: they submit with `form.dispatchEvent(new Event('submit'))`, which bypasses constraint validation, and jsdom's `requestSubmit()` fires the handler even on an invalid required field. Adding a native `required` leaves all 72 tests green. **`novalidate` has no unit-level defence and cannot have one** — task 5.3 owns asserting it in a real browser.

**One live doubt, with an owner rather than a shrug.** The two page specs call `fixture.whenStable()` after each interaction, which forces change detection; zoneless Angular re-renders only when the view is marked dirty. Every interaction tested here reaches the view through a template-bound listener, so the two should be equivalent — but the specs cannot tell the difference, and an interaction that updated form state outside a template event would leave them green and the screen stale. **Task 5.3 owns closing it**, with a Playwright journey that types an invalid value and asserts the message with nothing programmatic in the loop.

**Trade-off accepted:** `MIN_PASSWORD_LENGTH` and `MAX_PASSWORD_BYTES` are hand-copied from `app/schemas/auth.py` and `app/core/security.py`, and **nothing compares them** — the same drift `CONVENTIONS.md` documents for the upload limits, invisible until a user is rejected by a rule the form allowed. **Related, and proposed rather than done:** `RegisterRequest.display_name` is still `str | None = None` while its only client now requires it. There is no good argument for an API looser than its only caller; the fix is `str = Field(min_length=1, strip_whitespace=True)` at **task 0.10**, together with amending `04-API-SPEC.md`'s claim that every field but three "is `null` on a fresh account". No backend code was touched at 0.9.

## 071 — The display face is for chrome we author

**Decision:** `font-display` is used only on headings this project writes. Anything a user entered or a model generated renders in the body face. `userLabel(user)` returns `display_name?.trim() || email`.

## 072 — `Field(strip_whitespace=True)` does not exist, and the correction 070 specified had to be respelled

**Decision:** `RegisterRequest.display_name` is `Annotated[str, StringConstraints(strip_whitespace=True, min_length=1)]`, aliased as `DisplayName` in `schemas/auth.py`. `STAGE-0` task 0.10 and decision 070 both specified `str = Field(min_length=1, strip_whitespace=True)`; both are corrected to match the code rather than the code bent to match them.
**Alternative:** The specified spelling. Or `Field(min_length=1)` plus a `field_validator` that strips, mirroring `register.page.ts`'s `requiredText` in Python.
**Reasoning:** Pydantic v2's `Field` has no `strip_whitespace` parameter. Passing one is an *extra keyword argument*: it emits `PydanticDeprecatedSince20`, is filed under `json_schema_extra`, and strips nothing. Measured on pydantic 2.13.4 before either version was written:

```
Field(min_length=1, strip_whitespace=True)      '  Coral  ' -> '  Coral  '     not stripped
Field(min_length=1, strip_whitespace=True)      '   '       -> accepted
StringConstraints(strip_whitespace=True, …)     '  Coral  ' -> 'Coral'
StringConstraints(strip_whitespace=True, …)     '   '       -> ValidationError, loc ('display_name',)
```

**This matters more than a spelling.** The whole point of the correction is that the API should not be looser than its only client, and `register.page.ts` has rejected a whitespace-only name since 0.9 through a trim-aware validator (070). Shipped as specified, the API would have *accepted* `"   "` while the form rejected it — the same mismatch, in the same direction, with a line of code that looks like it closed it. The order inside `StringConstraints` is the other half: strip runs before `min_length`, which is what turns `"   "` into a `422` instead of a blank column. A hand-rolled validator would work equally well and was rejected only because it is a second place to get that ordering wrong. Against a `field_validator` there is one real argument for the annotation: `DisplayName` is a named type that `PATCH /me` can reuse at Stage 2 without restating the rule.
**Trade-off accepted:** The rule is inside an annotation rather than in a function with a name and a docstring, so it is less visible to someone skimming the file — mitigated by the alias and the comment above it. And **the response is untouched**: `UserResponse.display_name` stays `str | None`, because the column is nullable, four accounts predate this rule, and `PATCH /me` never sets it. Tightening a request body does not retrospectively tighten a column, and `04-API-SPEC.md` is amended for the request only.

## 073 — The test database is named by its own variable, and the guard runs before `app` is imported

**Decision:** `backend/tests/conftest.py` reads `TEST_DATABASE_URL` from the environment or `.env`, refuses to import if it is unset **or equal to `DATABASE_URL`**, and otherwise copies it into `os.environ["DATABASE_URL"]` **before the first `app` import**. The variable is read by a small `BaseSettings` class local to `conftest.py`, not by a field on `app.core.config.Settings`. `.env.example` gains the variable; the local container is `postgres:18` on port 5433.
**Alternative:** A `TEST_DATABASE_URL` field on `Settings`, which is what decision 021 would imply. Or monkeypatching `settings.DATABASE_URL` after import. Or passing a URL to alembic and to the engine separately.
**Reasoning:** 021 put configuration on `Settings` because services import it and cannot receive a dependency. That argument does not reach here: **the application has no test database.** A field on `Settings` would ship to Render, appear in `/docs`-adjacent tooling, and describe something no application code ever reads. The copy-into-`DATABASE_URL` approach is what makes everything else need no special casing at all — `settings`, `db.session.engine` and `alembic/env.py` all read `DATABASE_URL` already, so one assignment redirects the whole process and nothing is monkeypatched. The cost is that it only works before `app.core.config` builds its singleton, which is why the import order is stated in the module docstring and why an `assert settings.DATABASE_URL == TEST_DATABASE_URL` sits directly beneath the imports: the assumption that environment beats dotenv is turned into an import-time failure rather than a suite that quietly points elsewhere.
**On the guard, which is the part that earns its place.** This project's `DATABASE_URL` is a live Neon database holding real rows. A fixture that migrates and truncates is one stale `.env` away from destroying it. Both refusals were verified by pointing `TEST_DATABASE_URL` at the real Neon URL:

```
tests/conftest.py:38: RuntimeError: TEST_DATABASE_URL is not set. The suite creates and
  drops rows, so it refuses to guess at a database.
tests/conftest.py:44: RuntimeError: TEST_DATABASE_URL is the same database as DATABASE_URL.
```

Both fire at module import, before any engine exists — grepping the run for driver activity returns zero lines, so the refusal is not "it connected and then declined".
**Trade-off accepted:** Three things. The import order is load-bearing and invisible — moving one `app` import above line 50 silently redirects the suite, and only the comment and that assertion stand between a reader and that outcome. There is a second `BaseSettings` subclass in the repository that is deliberately not the first one. And **every test run now requires `TEST_DATABASE_URL` to be present**, including `pytest tests/unit`, which needs no database — the variable must exist, though nothing has to be listening on it, because the schema fixture is not autouse.

## 074 — One transaction per test, and the two things that prove the fixture works

**Decision:** The schema comes from `alembic upgrade head`, once per session. Each test gets a `Connection` with an open transaction and a `Session` bound to it with `join_transaction_mode="create_savepoint"`; the transaction is rolled back afterwards and never committed. A session-scoped teardown compares `users` and `items` row counts from before and after the run and fails if they moved.
**Alternative:** `Base.metadata.create_all()` for the schema, which is what `db/base.py`'s comment and `02-DATA-MODEL.md` both describe. `TRUNCATE items, users RESTART IDENTITY CASCADE` between tests instead of a rollback.

**Corrected before task 1.1, and the correction was wrong the first time.** This entry left the false claim standing in three places — `02-DATA-MODEL.md`, `app/db/base.py` and `app/models/item.py`, the third of which this entry did not name — because 0.10 was a test task and two of the three are application code. A reader opens the file before they open the document, so leaving the comment for the document to contradict was the wrong half to fix first.

The replacement first written for `db/base.py` said the convention is what 037, 040 and 052 match on. **That is also false, and the mutation caught it before it was pasted:** changing the `uq` convention breaks nothing at all, because the live schema is built by migration `0001` and the name PostgreSQL reports comes from the migration's literal, not from the ORM's metadata. Changing the string the *route* matches on is what fails a named test — `test_register_rejects_a_duplicate_email` and `test_upload_retries_the_batch_when_a_short_id_collides`, plus one more each. The convention's actual job is narrower and worth stating exactly: it keeps the model and the database from describing one constraint under two names. See 077 for the seam this exposed and the test that now covers it.
**Reasoning:** `create_all` cannot build this schema and the two documents describing it are wrong. Measured against a mock dialect: it emits two `CREATE TABLE`s and one `CREATE INDEX`, and **no `CREATE TYPE` and no `CREATE EXTENSION`** — decision 024 put `create_type=False` on all three enum objects, so a virgin database fails on `item_status`, and on `CITEXT` before that. Migration `0001` does create both extensions, confirmed by running `upgrade head` against an empty `postgres:18` container and reading `pg_extension` back. The savepoint mode was measured rather than assumed, because `_insert` calls `db.rollback()` itself on a `short_id` collision and that is the exact behaviour the retry test exercises: with `create_savepoint` the route's rollback releases to its own savepoint, the outer transaction reports `is_active: True`, the retry commits, and the outer rollback still empties the database. `TRUNCATE` would sidestep the question at two extra round trips per test and is the fallback if this ever stops holding.
**One consequence of running alembic in-process:** `alembic.ini`'s `version_path_separator` is superseded by `path_separator` in alembic 1.18, and the deprecation warning fires when `command.upgrade` processes `prepend_sys_path` — not when `Config` is constructed. It has been firing since alembic was upgraded and nobody saw it, because Python hides `DeprecationWarning` by default and the CLI is the only place it had ever run. pytest shows warnings, so this task is what made it visible. The key is renamed here rather than carried into Stage 1: a warning that fires on every run is one nobody reads. `version_locations` is not set in this project, so the key governs only `prepend_sys_path`, whose single entry contains no separator either way — the rename is verified to change no behaviour, with `downgrade base` and `upgrade head` run again after it.

**The count check exists because the rollback is the single most deletable line in the file.** Turn `transaction.rollback()` into `transaction.commit()` and every assertion in the suite still passes — the tests are written against data they created, so they do not care whether it survives. What changes is that the database fills up and later runs collide with earlier ones. Verified: the mutation leaves `192 passed` and produces one teardown error reading `tests leaked rows into the test database: {'users': 28, 'items': 24} -> {'users': 56, 'items': 48}`. Counts rather than "is empty", so a database left dirty by a crashed run does not blame this run for it.
**Trade-off accepted:** pytest attributes a session-scoped teardown failure to the last test that used the fixture, so the leak is reported against `test_storage.py::test_raises_when_the_response_carries_no_public_id`, which has nothing to do with it. The message names the real cause; the test name does not. Accepted because the alternative — an ordinary test asserting emptiness — would have to run last, and a test whose correctness depends on collection order is worse than a misfiled error.

**And the second trade-off, which is the one worth reading twice: nothing guards the guard, and that is accepted rather than unnoticed.** Delete the count check and all 192 tests still pass. It is the only thing standing between a stale `rollback()` and a test database that silently fills up, and it is defended by nothing but this paragraph. **A reader might delete it, and nothing would stop them.** That was put to the test deliberately and there is no structural answer: any check living in the same file as the thing it checks is removable in the same edit, and whatever were added to guard *that* would be unguarded in turn. The regress does not terminate in code. It terminates here and in `CONVENTIONS.md`, which is why both say so explicitly rather than leaving the reader to infer that a line with no test behind it is dead weight. Two narrower ideas were considered and rejected: moving the check into the per-test `connection` fixture, which would attribute a leak to the test that caused it but costs two round trips on every test and is exactly as deletable; and asserting the tables are empty at session start, which blames this run for a database a previous crashed run left dirty. **The failure mode is also local-only** — CI gets a fresh service container every run, so a leak is invisible there and shows up only on the developer's machine, slowly.

**Decision:** The `for item in items: db.refresh(item)` loop in `items.py`'s `_insert` is not removed at task 0.10, and the comment above it — "SessionLocal sets `expire_on_commit=False`, so the server defaults this response needs are not otherwise fetched" — is recorded here as **measurably false** rather than corrected in place.
**Alternative:** Delete the loop, since nothing needs it. Or leave it with no note, since it is harmless.
**Reasoning:** It was the one mutation of thirteen that survived.
```
app.main disabled before fileConfig: False
app.main disabled after  fileConfig: True
```

## 077 — The naming convention has no runtime effect, and the two artefacts are compared directly

**Decision:** `tests/unit/test_db_naming.py` asserts that `Base.metadata` produces exactly the eight constraint names migration `0001` spells out, and that the two names a route matches on appear literally in `0001`'s source. It reads the migration as **text** rather than running it.

**Alternative:** A Pydantic model and `.parse()`, which is idiomatic in openai 2.x and gives a typed result. Enum arrays written out as `03-AI-CONTRACTS.md` prints them. The vocabulary block appended to the end of the prompt file with no placeholder.
**Reasoning:** On `.parse()`: it generates a schema from the model, and **the schema this task exists to verify is the one the document wrote down** — including a nullable enum expressed as `{"type": ["string", "null"], "enum": [...]}`, where Pydantic emits `anyOf`. Verifying a generated variant would prove nothing about the contract, and the strict-subset notes in `03` are specifically about hand-written JSON Schema. On deriving `required`: strict mode rejects a schema where `required` and `properties` differ, so a second hand-written list is one forgotten edit from a `400` that reads as a model fault.

On generating the enum arrays, the cost is real and is recorded rather than glossed. **`06-TESTING-STRATEGY.md`'s Layer 2 contract test becomes a tautology.** Its stated purpose was to catch someone adding `burgundy` to the prompt but not to the enum; with prompt, schema and validator all rendered from `enums.py`, that drift is structurally impossible and a comparison between two expressions of one source proves nothing. The trade is still right — a structural guarantee beats a test — but a test whose docstring claims a coverage it no longer has is worse than no test, so `06` is corrected in the same commit and names the real remaining seam: `02-DATA-MODEL.md` → `enums.py` → `enums.ts`, hand-maintained, three copies, nothing comparing them.

On the placeholder: appending would work identically, and the placeholder makes the prompt file honest about what it becomes — someone reading it alone otherwise sees a prompt with no vocabulary and no sign one is coming. The guard raises at import because a prompt that silently lost its vocabulary still returns plausible tags. **`fit`, `length` and `rise` are plain strings in the schema** — an out-of-vocabulary value there is coerced to null rather than retried, so constraining them would buy nothing — which means the rendered block is the *only* place the model ever learns those three vocabularies. Losing it degrades exactly the three fields nothing else would catch. The guard is covered by `test_a_prompt_file_without_the_placeholder_raises_at_load`, not merely intended.
**Trade-off accepted:** No typed result object — `tag_item` returns `dict[str, Any]` and 1.2's `ItemTags` is where types arrive. And `03-AI-CONTRACTS.md`'s printed schema is now a *description* of generated output rather than the literal source, so the two can drift if `enums.py` changes and the document is not updated. That is the same seam named above and it is the one this project has always had.

## 083 — The `vision` transform pins the format, and what that did and did not catch

**Decision:** `Transform.VISION` moves from `w_800,c_limit,f_auto,q_auto` to `w_800,c_limit,f_jpg,q_auto`. `detail` keeps `f_auto` and is unchanged. `07-DEPLOYMENT.md`'s table, `03-AI-CONTRACTS.md`'s input line and `01-ARCHITECTURE.md`'s flow step 7a are corrected to match.
**Alternative:** Keep `f_auto`, which the measurement below does not disprove.
**Reasoning — and the first thing to say is what was *not* found.** 046 left this open as a suspected failure: `f_auto` on a HEIC original, delivered to a client sending no `Accept` header, might fall back to the format named by the file extension, and these URLs deliberately carry none. **That failure did not occur.** One real iPhone HEIC, 2,047,391 bytes, uploaded and fetched three ways through the `vision` transform:

```
no Accept header         image/jpeg
*/*                      image/jpeg
browser-like             image/webp
```

The two requests that most resemble what a non-browser fetcher sends both returned JPEG, and only a browser-like `Accept` produced WebP — which OpenAI reads anyway. **The live vision call in task 1.1 was then made against the `f_auto` URL and it worked**, returning fifteen valid fields. So on this sample the path OpenAI most likely took was already safe, and nothing was broken at the moment the change was made.

**What was caught is an unobservable variable, not a live failure.** `f_auto`'s answer is a function of the `Accept` header of whoever fetches the URL. For every other transform in the table that client is a browser, which is what `f_auto` exists to serve. For `vision` it is OpenAI's fetcher — we cannot see the header it sends, we cannot control it, and it can change without notice on their side or on Cloudinary's. **Format negotiation cannot help us here: OpenAI is not a browser and gains nothing from a smaller modern format, so the only thing negotiation can do on this URL is one day return something the model cannot read.** Removing a variable that only has a downside is worth one word in a string, and it is worth it *before* the golden-set run at 1.11 rather than in the middle of it, where a silent format change would look like an accuracy regression.

**This is exactly why the criterion was three requests rather than one.** The stage file's original test — "if it comes back `image/heic`, change it" — would have passed on the first line and closed the question with `f_auto` still in place and the real variable undisturbed. The three-header form is what surfaced the disagreement, and the disagreement is the finding.
**Trade-off accepted:** `vision` no longer benefits from any future format Cloudinary adds, which for a machine consumer is no loss. Delivery is marginally larger than a negotiated WebP, on one fetch per item, which is invisible next to the model call it feeds. And the split between `detail` and `vision` that 046 defended as hypothetical is now load-bearing: they hold different strings, so anyone tidying them back into one entry breaks this. `test_the_vision_transform_pins_the_format_rather_than_negotiating` exists to say so by name rather than only through the table-comparison test, which would fail with a message about a string.

## 084 — `validate_tag_dict` checks membership and never checks whether the member belongs with the category

**Decision:** Recorded as **one gap with three instances**, not three unrelated bugs. Task 1.2 owns the decision and must make it rather than defer it again; "the asymmetry stays" is an acceptable answer that has to be chosen and written down.
**Alternative:** Treat 082's `layer` finding and the `fit` finding below as separate patches, fixing whichever is in front of you.
**Reasoning:** The validator tests every descriptive field against a **flat** vocabulary. Two fields already escape that — `subcategory` through the `SUBCATEGORIES` map, and `rise` through an explicit bottoms-only gate — so the shape of the fix already exists in the file twice over. Everything else is membership only, which means a value that is a legal member of its own enum and nonsense beside its category passes with no error and no coercion.

Three instances, in descending order of how much they cost:

- **`layer`** (082). `{"category": "top", "layer": "standalone"}` validates clean. `layer` is what the stylist's layering constraint keys on, so the resulting look is silently wrong rather than visibly invalid.
- **`fit`**. `{"category": "top", "subcategory": "tank", "fit": "skinny"}` validates clean. `skinny` is a trouser word. The stylist prompt reasons on `fit` for proportion — *"Skinny and slim bottoms balance volume above"* — so a wrong `fit` degrades styling advice rather than breaking structure.
- **`length`**. Untested and unobserved, and 029 accepted the risk deliberately.

**029's premise has been falsified in the neighbouring field, which is why this is a decision and not a bug report.** That entry rejected a per-category map for `length` on the grounds that "the three axes do not collide in practice — the vision model does not offer `maxi` for a t-shirt", and set the condition for revisiting as the Stage 1 golden-set run. The model offered `skinny` for a tank top on the seventh image anyone ran, before the golden set exists. `maxi` on a t-shirt and `skinny` on a tank top are the same sentence.

**A second and genuinely separate problem surfaced beside it, and the two must not be conflated.** `fit: "flared"` — a value in no vocabulary at all — is caught by the membership check and coerced to null. The validator works exactly as designed. What is missing is any *record*: `TagValidation.coerced` carries the discarded value at validation time, `03-AI-CONTRACTS.md` has the vision path coerce silently by design, and nothing persists it. So a real garment attribute the model observed is dropped, the item screen shows an empty field, and no trace survives that a value was ever returned. `items.attributes` is a `JSONB` column that exists to absorb exactly this kind of thing without a migration; whether rejected values belong there is 1.3's call, and logging them is 1.2's. **That gap is about membership working and nobody watching, where the gap above is about membership not being enough.**
**Trade-off accepted:** Naming this as one rule invites one generic mechanism, and a generic per-category allow-map is what 029 rejected for reasons that have not gone away — it doubles the validation surface, the seed data's exposure to it and the test matrix. The mapping is also not equally writable per field: `layer`'s is close to total (standalone categories → `standalone`, outerwear → `mid` or `outer`, bottoms → `base`), while `fit`'s is fuzzy and a fuzzy allow-map manufactures false coercions. A per-category **deny** list is a smaller and more defensible claim than an allow-map and is worth considering for `fit` alone. None of that is decided here, deliberately — 1.2 owns the validator.

**Amended at task 1.2a — the `layer` list above is wrong in the one place that mattered, and it would have propagated.** It describes the map as "close to total" and then names only four of the seven categories: standalone categories, outerwear, and bottoms. **`bottoms → base` was not implemented anywhere** — it is a claim this entry made about code that did not exist — and **`top` is missing from the list altogether**, which is the single category that makes the map *close to* total rather than total. Anyone implementing from this sentence would have written a total map and, in doing so, silently decided that a top tagged `standalone` becomes `base` — the guess 082 exists to refuse. Both are settled in 085; the general rule this entry states is unchanged and correct.

## 085 — Category-dependent validity is one rule with one shape, and `top` is the only category it cannot answer for

**Decision:** `app/enums.py` gains three tables and `validate_tag_dict` gains one judgement: **is this value one the category it arrived beside can be described by?** The response is not new policy — it is the field's existing policy. `FIELD_APPLIES_TO` says which categories a field describes at all (`fit`: top, bottom, dress, outerwear; `length`: everything but bag and accessory; `rise`: bottom, which generalises the gate already in the file). `VALUE_APPLIES_TO` narrows individual words that are narrower than their field: `skinny` to bottoms, `wide` to bottoms and dresses, `bodycon` to everything but outerwear, the three sleeve words to top/dress/outerwear, the three hem words to bottom/dress/outerwear. `LAYERS_BY_CATEGORY` gives every category an admitted set and an answer. `CATEGORY_DEPENDENT_FIELDS` exports the five field names so `PATCH /items/{id}` reads the list rather than restating it. `_STANDALONE_CATEGORIES` is deleted: it is now four rows of the layer table. All three tables are public because task 1.2b renders them into the prompt's `{{VOCABULARY}}` block.

**Alternative:** One generic per-category allow-map per field, which is what 084's framing invites. Coercing a `top` tagged `standalone` to `base`, which is what 082 called a guess and what 084's own sentence would have produced. Leaving the asymmetry, which 082 said was an acceptable answer if chosen. Mirroring the rules into `enums.ts` so 1.9's tag editor can filter its selects.

**Reasoning — the rule is one pair, applied five times.** Which values the category admits, and what the category says the answer is when the value is not admitted. Where the category determines a single answer the rule coerces to it; where it does not, the vocabulary reports an error, which the vision path turns into one retry naming the violation and `PATCH` turns into a `422`. **Nothing invents a value.** Both halves already existed in the file — `SUBCATEGORIES` is the error case, the bottoms-only `rise` gate is the coercion case — so this is a generalisation of two rules rather than a new mechanism.

**The answer comes from the document naming one, not from the arithmetic of the admissible set.** This is the part most likely to be re-derived wrongly. `outerwear` admits **two** values, `mid` and `outer`, and still has a determinate answer — `outer` — because `02-DATA-MODEL.md` says a coat is outer. `top` also admits two, `base` and `mid`, and has **no** answer, because the document names none and both are legitimate. So cardinality is not the test; the document is. **An implementation that derived the answer from the size of `admits` would turn `outerwear` into an error path and break `test_outerwear_with_a_base_layer_is_coerced_to_outer`** — a documented, tested coercion silently reversed by a plausible-looking simplification. That is precisely why `LayerRule` stores `answer` as a field rather than computing it, and why a later reader should not tidy it into a derivation.

**The three tables have three shapes, and the asymmetry is structural rather than untidy.** `fit`, `length` and `rise` are the three fields `02-DATA-MODEL.md` declares always nullable, so their answer is `NULL` by construction: any other answer would be a substituted value, which is the one thing this rule forbids. There is nothing for a second field to hold, so those two tables hold only categories. `layer` is not nullable by design — it sits in `_STRICT_ENUM_FIELDS` and the stylist's layering constraint keys on it — so it is the only field that has to name something, and therefore the only table with room to. Three tables, three shapes; do not make them uniform. `VALUE_APPLIES_TO` is separately nested by field rather than keyed by value alone because **`mid` is a member of both `Rise` and `Layer`**, so a flat value-keyed map would be ambiguous the moment a rule touched either.

**Which fields opt in, including the part that does not.** `layer` opts in fully. `fit` opts in twice — an applicability gate and three narrowed words. `length` opts in twice as well, but only at the two ends of its flat list: the sleeve words and the hem words, which belong to exactly one axis each. The middle five — `crop`, `regular`, `longline`, `ankle`, `full` — are left unenforced on purpose, because they genuinely span axes (cropped trousers and a cropped top, ankle boots and ankle trousers) and a rule over them would coerce correct answers away. 029's cost argument survives intact in that gap; what does not survive is its premise, and 029 is closed.

**An unrecognised `category` fires no category-dependent rule at all.** Every rule here is keyed by the category, so when it is not in the vocabulary there is nothing to look up rather than something to report a second time — and the membership check has already reported the one real fault. Reporting four consequences of it would bury the cause in the retry text 1.2b builds from `TagValidation.reason`. `subcategory` predates this and still double-reports; unifying that would be re-litigating a rule from task 0.4 and is deliberately not done here.

**The rules stay server-side.** `enums.ts` mirrors the vocabulary's *values* and not its rules. The alternative adds a hand-written copy in a second language with nothing comparing it to anything — the same position `CONVENTIONS.md` already records for the upload limits and the password rules — and it would have been written before the screen that wants it existed. What 1.9 gets instead: the editor may offer `skinny` for a tank, and the server answers `422` naming the field. That is a visible, recoverable failure, and it is only safe because the clearing rule below keeps a category change from producing the same `422` on an otherwise correct request. If it ever matters enough to fix, the fix is an endpoint publishing the vocabulary — which needs `04-API-SPEC.md` changed first, since that document forbids adding endpoints.

**Measured rather than asserted.** The eight responses task 1.1 observed were replayed through the new rules, each row carrying only the fields `STAGE-1` 1.11 recorded, since an absent key is never invented: both known-wrong answers are caught by two different mechanisms — `fit: "flared"` by membership, which already worked, and `fit: "skinny"` on a tank by this entry's rule — and the other six are untouched, including `bodycon` on a bodysuit and `wide` on jeans, which the narrow tables must not reach. Seven mutations plus a fatal control were run from a pristine copy with a green baseline verified at both ends; all eight were caught. `tests/unit/test_enums.py` pins each table **literally** as well as behaviourally, because a behavioural test that reads its expectation from the table adapts to a mutation of the table — mutation 5 is caught by exactly one test in 376, and that test is the literal pin.

**Trade-off accepted:** **An item can now finish `failed` with no tags at all where it previously finished `ready` with a wrong `layer`.** That is the cost of refusing to guess, and it is the right side of the trade: a failed tile is visible and carries a retry button and an "Add manually" link, whereas a wrong `layer` is invisible until Stage 2 builds a look on it, with nothing pointing back here. The alternative — correcting a top to `base` — would push a hoodie the model answered `mid` about, correctly, to the wrong value across a whole class of garments, silently, and far more often than the error will fire. Two smaller costs: the validation surface and the test matrix are larger, which is exactly what 029 was unwilling to pay and is now paid deliberately; and `PATCH` clears five fields on a category change rather than three, so a `top → dress` edit discards a `fit` that was valid. 030 accepted that shape of loss for `layer` already and now says five.

## 086 — `validate_tags` judges one answer at a time, and the two failures it can end in are not the same failure

**Decision:** `async validate_tags(raw: dict[str, Any], image_url: str) -> ItemTags` in `app/services/vision.py`. It reads `validate_tag_dict`'s report, logs every coercion, retries **once** through `tag_item(image_url, correction=…)` naming the violation, and raises `TaggingError` — defined here, beside `StorageError`'s shape (044) — when the second answer is unacceptable too. `ItemTags` is a frozen slotted dataclass typed with the vocabulary classes, carrying the accepted answer's `coerced` issues and nothing else. Eleven non-nullable fields absent, `null` or blank are a violation like any other. The `confidence < 0.35` branch is **not** built and no settings field is added. 028 is struck in the two places this contradicts.
**Alternative:** `validate_tags(raw)` as three documents printed it, which cannot retry. A third function owning call-validate-retry so 1.3 has one entry point. A Pydantic `ItemTags`. Carrying both attempts' coercions. Building the confidence branch as 028 and `03`'s table specified.
**Reasoning — the signature was the contradiction, and the fix names a boundary rather than patching a parameter list.** A retry is a second call to the model, so the function that owns the retry needs the URL; that much is arithmetic. What the arithmetic exposed is that **`tag_item`'s failures and `validate_tags`'s failures are different facts about the same item.** A `ValueError` or a provider exception says no usable answer arrived. `TaggingError` says the model answered and the answer could not be accepted. 1.3 writes `failed` for both and writes different `error_message`s, so the two are worth keeping apart — which is what settles the third-function alternative against itself: an orchestrator would hand 1.3 one exception type and throw the distinction away to save it three lines. The cost is that 1.3 wraps the first call itself and `TaggingError` is raised from one module while the naked call sits in another. `vision.py`'s docstring said "task 1.2 wraps both", which was never achievable under the documented signature and is corrected rather than honoured.

**The eleven required fields are what makes `ItemTags` constructible, and they belong here, not in the vocabulary.** `validate_tag_dict` reads every field with `.get`, so an absent key and a `null` one are one thing to it and both pass. That is *correct* — `PATCH /items/{id}` sends three fields and must not be told the other twelve are missing — and it means `{}` is a clean report. Building a typed object from a clean report that has no `category` is a `TypeError` escaping a background task, where the row stays `processing` until 1.3's sweep instead of finishing `failed` with a message. So the check lives in the service, keyed to the schema: the eleven are exactly the properties with no `null` in their type, asserted against `VISION_SCHEMA` rather than restated. Strict mode should make the row unfireable, which puts it in the same class as the first and third rows of `03`'s table — a check that exists because the guarantee is somebody else's.

**A blank `display_name` counts as missing, which is a narrowing and is chosen rather than inherited.** `validate_tag_dict` checks `isinstance(str)` and nothing more, so `""` passes and 1.3 writes a tile with nothing on it. One condition, and the failure it prevents is the only one in the eleven that a user would see rather than a developer.

**`ItemTags.coerced` carries the accepted answer's coercions and no others, and this is the part most likely to be widened by someone being generous.** When the first answer is rejected and the retry is accepted, the first answer's discarded values describe tags that were never written — carrying them would let 1.3 record "`fit` was discarded" in `items.attributes` beside a row whose `fit` came back fine on the retry, which is not a fuller record but a false one. Nothing is lost: **every coercion from every attempt is logged**, with the field, the rejected value and the category it arrived beside. That log is the record 084 found missing — `fit: "flared"` on real jeans, correctly nulled, remembered by nothing — and it is deliberately not classified into "out of vocabulary" and "wrong for its category" at write time, because 1.11 has to count those apart and the field plus the value already answers which is which. Classifying it would mean a `kind` on `TagIssue`, which is 1.2a's file and its literal pins reopened for something already in the line.

**The confidence branch is not built because both of its branches do the same thing.** `03`'s row read *accept, but set `status='ready'` and flag for review in UI* — and an item above the threshold is also `status='ready'`. The only difference was a flag, and `05-FRONTEND-SPEC.md` names no review surface, no stage file mentions confidence, and 028's "against `settings`" named a field nobody had written. A branch whose sole output is a flag nothing reads is dead code. The evidence says the same thing louder: eight live responses at 1.1 returned `0.9` every time **including both wrong ones**, so the threshold would have flagged nothing in eight images while missing both errors. The number is not discarded — 1.3 persists it as `ai_confidence` and 1.11 mines it — so a threshold introduced later can be applied over the whole table, which is a better instrument than one frozen at tag time. The prompt still asks for the self-assessment and still names 0.35, because that is what the number honestly describes: the photograph, not the answer.
**Trade-off accepted:** **Three things a later reader may mistake for oversights.** `TaggingError` is raised from `vision.py` while an equally fatal `ValueError` is raised from a different call in the same module, so 1.3 must catch two types — deliberate, and the reason is above. `_REQUIRED_FIELDS` duplicates a fact the schema already states, guarded by a test that compares them rather than by a comment. And `03`'s table now has a row that strict mode makes unreachable on model output, which reads as belt-and-braces until `PATCH` or a future provider makes it the only thing standing between a short answer and an unhandled exception.

## 087 — The prompt is told the rules, not only the words, and the rendered result has a version

**Decision:** `_vocabulary_block()` renders `FIELD_APPLIES_TO`, `VALUE_APPLIES_TO` and `LAYERS_BY_CATEGORY` into `{{VOCABULARY}}` the way it already rendered `SUBCATEGORIES` — 080's property extended from the values to the rules. Each category's **answer** is not rendered, and the five unenforced `length` words get no rule line. `vision_system.md` loses the two sentences that hand-wrote rules the block now generates. `PROMPT_VERSION` is the first twelve hex characters of the SHA-256 of `SYSTEM_PROMPT`, taken after the render.
**Alternative:** Leaving the block as nine `fit` words with no category guidance, which is what made every category-dependent coercion a silent one. Rendering the answers as well. A hand-bumped version string, or none at all until 1.11 needs one.
**Reasoning:** Strict mode guarantees membership and nothing else, so `layer: "standalone"` on a top passes the schema perfectly and `fit: "skinny"` on a tank passed everything until 1.2a. The validator now catches both, but a validator that catches without telling produces exactly what 084 complained about — a coercion nobody learns from, and in the `top` case an item that finishes `failed`. Telling the model is the cheap half of the fix and it does not weaken the validator, because a prompt is not a guarantee (082).

**What is deliberately not rendered is the more interesting half.** The **answer** — bottom becomes `base`, outerwear becomes `outer` — is what *this layer does with a wrong value*, not something the model needs; printing it invites the model to reason about our correction rather than about the garment. And `crop`, `regular`, `longline`, `ankle` and `full` get no rule line at all, because `02-DATA-MODEL.md` leaves them unenforced on purpose: rendering a narrowing the validator does not apply would teach the model a rule this project does not hold, which is the one way this block can make the output worse rather than better. `test_the_middle_of_the_length_list_gets_no_rule_of_its_own` is what fails if someone renders all eleven for symmetry.

**The version is hashed because half the prompt is generated.** Task 1.11 measures accuracy against this prompt and records the version beside the model id, for the same reason 078 pinned a dated snapshot rather than an alias: a curve measured against something that moved underneath it is not reproducible. A hand-bumped constant is wrong the moment a table in `enums.py` changes and nobody remembers the constant — and that error is invisible until an eval run is compared against a prompt no one can reconstruct. Hashing the **rendered** text rather than the file is the whole point; hashing the file would hold still while the vocabulary moved. **Persisting it beside the tags is 1.3's**, so a row tagged today can be traced to the prompt that tagged it; 1.11 records it in `docs/eval-results.md`.
**Trade-off accepted:** The prompt is roughly 40% longer, at about 150 extra tokens per call — a fraction of a cent across the whole project, and cost was never the constraint here. Two costs that matter more. **Nothing measures whether the longer prompt helps**, and it could plausibly hurt: more instruction is more to ignore, and the `top`/`layer` error may now fire so rarely that the give-up path is exercised only by tests. That is 1.11's to find, which is exactly why the version exists. And `PROMPT_VERSION` is imported by nothing until 1.11 — a symbol with no reader for one task, accepted because the alternative is 1.11 hand-typing a version for a prompt that has already moved twice.
